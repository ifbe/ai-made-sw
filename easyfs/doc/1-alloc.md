## 1. 结论先行

1. 空闲管理用**位图**：`1 bit` 代表 `bit_unit` 字节（v0：`bit_unit = chunk_size`，默认 4 KiB）。`1 = 已用`，`0 = 空闲`。
2. 位图块**不是定长 4K**：每块自己声明占多少字节（`block_bytes`），随卷放大 —— 256 MiB 卷用 4 KiB 块，16 TB 卷用 1 MiB 块。
3. 每块**自描述它管理的那片区域**：`region_delta`（相对本块起点的自相对偏移，可负）+ `region_bytes`（总字节数）+ `region_logical_start`（区域起点在逻辑坐标 `L` 里的位置）。
4. 所有位图块用通用块头的 `prev_delta` / `next_delta` 串成**双向链**，链序 = 区域位置升序；链头由 anchor 的 `alloioff` 指向。
5. 位图块的位置**只**记在 anchor + 链里，**绝不放在位图自己里**（否则自举循环）。
6. 位图是**派生数据**：恒等于「从根可达的块集合」的补集，任何时候都能全量重建。
7. 因为区域用**自相对 delta** 描述：**左右伸缩都只是增删链两端的块；整卷平移零改动**。

## 2. 位图语义

- **bit → 物理地址**：`P = 块地址 + region_delta + bit号 × bit_unit`
- **物理地址 → bit**：先找区域（§2.2），再 `bit号 = (P − region_start) / bit_unit`
- `1 = 已用`，`0 = 空闲`；bit 号在块内从 0 递增；字节内 **bit 0 = 最低位**（LSB first）
- 每个 bit 覆盖 `[P, P + bit_unit)` 这一段连续空间
- 有效 bit 数 = `ceil(region_bytes / bit_unit)`；可用 bit 数 = `payload_len × 8`；必须 `有效 ≤ 可用`
- **不变量**：所有块的管理区域**首尾相接、互不重叠**，并集 = `[data_lo, data_hi)`（fsck 校验）
- **anchor 所在的 4 KiB 不属于任何区域**（几何固定，天然已用，不需要 bit）
- 永久元数据（位图链自己、所有 dir / link / bad 块）占用的 bit 恒为 1
- **一次分配不能跨两个块（区域）**：单次最大连续分配 = 该区域内最长的连续 0 段

### 2.1 `bit_unit`（每个 bit 代表多少字节）

* **格式能力（不写死）**：`bit_unit` 是**每个位图块自己的字段**（`BM_OFF_BIT_UNIT`，见 §3.2）
  ⇒ 不同区域可以有不同的粒度，甚至同一区域的不同块也可以不同。
  约束只有：**2 的幂**、**≥ `chunk_size`**、且 `region_bytes` 是它的整数倍
  （**最后一个区域例外**：末位是"半格"，按 `region_bytes` 截断，不允许越界）。
* **v0 策略（写死 4 KiB）**：`bit_unit` 恒等于 `chunk_size`。原因**不在格式，在于缺一台机器**：
  一旦某区域的 `bit_unit` 比 `chunk` 粗，就必然出现"只要一小块"的分配落在它里面 ——
  没有**分裂**就只能整格给出（浪费）或跨区域（本文件 §2 最后一条明令不允许）。
  ⇒ 启用混合粒度 = 补上"粗粒度起步 + 按需分裂"，设计见 §13（合并暂不做，见 §13.5）。
* **粗粒度的两个收益**：位图元数据小两三个数量级；`alloc` 要扫的 bit 数少同样多（§6.2 的性能瓶颈）。

### 2.2 怎么从物理地址找到块

| 卷规模 | 做法 |
|---|---|
| 小卷（几块 ~ 几百块） | 顺链走，比较 `region_start ≤ P < region_start + region_bytes` |
| 大卷（16 TB → 513 块） | 在 RAM 里维护 `(region_start, block_delta)` 有序数组（≈7.5 KB），二分 |

顺序访问时缓存"上一次用到的块"，只比较边界即可，不必每次从头找。

## 3. 位图块的结构

```
┌──────────────────────────────── block_bytes ────────────────────────────────┐
│ 通用块头 64 B │ 位图扩展 32 B │ 预留 (header_bytes−96) │ 位图数据 payload_len B │
└───────────────┴───────────────┴───────────────────────┴───────────────────────┘
                 ←──────────────── header_bytes ────────────────→
```

### 3.1 通用块头（64 B，见 [`common.md`](common.md)）

位图块里各字段的取值：

| 字段 | 取值 |
|---|---|
| `block_type` | **1** |
| `prev_delta` / `next_delta` | 链上前/后一块（按**区域位置**升序），自相对 i64，0 = 无 |
| `seq` | 本块在链上的序号（= 区域序号），沿链单调递增 |
| `header_bytes` | **类型专属区起点**：位图块 ≥ 96；其它类型恒 64 |
| `payload_len` | **位图数据字节数** = `block_bytes − header_bytes` |
| `payload_crc32` | **暂不启用**（见 §7.5） |
| `header_crc32` | 覆盖 `[0, header_bytes)`，即 **64 B 通用头 + 32 B 位图扩展**（见 §3.2） |

### 3.2 位图扩展（32 B，固定在 64..95）

| off | size | 字段 | 说明 |
|---|---|---|---|
| 64 | 8 | `region_delta` (i64) | 管理区域起点相对**本块起点**的偏移（自相对，可负） |
| 72 | 8 | `region_bytes` (u64) | 管理区域总字节数 |
| 80 | 4 | `block_bytes` (u32) | **本块占用的总字节数**（`chunk_size` 的整数倍） |
| 84 | 4 | `bit_unit` (u32) | **1 个 bit 代表多少字节**（2 的幂） |
| 88 | 8 | `region_logical_start` (i64) | 本块管理区域起点在**逻辑坐标 `L`** 里的位置（见 [`layout.md`](layout.md)）。用于按 `L` 定位数据、以及 fsck 的双向校验 |

### 3.3 三个尺寸字段的关系（互为校验）

```
block_bytes  = header_bytes + payload_len          ← fsck 必查
可用 bit 数  = payload_len × 8
有效 bit 数  = ceil(region_bytes / bit_unit) ≤  可用 bit 数
覆盖字节数   = 可用 bit 数 × bit_unit
```

### 3.4 尺寸选型（`bit_unit = 4 KiB`）

| `block_bytes` | `header_bytes` | `payload_len` | 可用 bit | 覆盖空间 |
|---|---|---|---|---|
| **4 KiB** | **96** | **4000** | 32,000 | **125 MiB** |
| 64 KiB | 96 | 65,440 | 523,520 | 2.0 GiB |
| 256 KiB | 96 | 262,048 | 2,096,384 | 8.0 GiB |
| 1 MiB | 96 | 1,048,480 | 8,387,840 | 32.0 GiB |
| 1 MiB（payload 取整数） | 48,576 | 1,000,000 | 8,000,000 | 30.5 GiB |

| 卷大小 | 自动选出的块大小 | 每块覆盖 | 位图块数 | 位图总量 |
|---|---|---|---|---|
| 32 MiB | 4 KiB | 125 MiB | 1 | 4 KiB |
| 256 MiB | 4 KiB | 125 MiB | 3 | 12 KiB |
| 1 GiB | 4 KiB | 125 MiB | 9 | 36 KiB |
| 16 GiB | 4 KiB | 125 MiB | 132 | 528 KiB |
| 1 TiB | 64 KiB | 2.0 GiB | 513 | 32.0 MiB |
| **16 TB** | **1 MiB** | **32.0 GiB** | **513** | **513 MiB** |

### 3.5 anchor 里与位图有关的字段

| anchor 字段 | 含义 |
|---|---|
| `data_lo_logical` | **数据区起点的逻辑坐标**（见 [`layout.md`](layout.md)） |
| `allotype` | **分配结构的类型**：`1` = 扁平位图链（现状）、`2` = 分配器**对象**（结构放链接块里；`bitmap_OBJECT`，将来）|
| `alloioff` | 自相对 delta，指向分配结构的**入口**（链头 / 链接块 / 树根，由 `allotype` 决定）|
| `allocnum` | 块数（链长 / 对象覆盖的块数，交叉校验用）|
| `allosize` | 所有位图块的 `block_bytes` 之和（交叉校验用）|
| `flags.bit0` | **clean**：上次是否干净卸载（见 §7.3） |

anchor 的完整字段表在卷布局文档里写（未定稿）。

## 4. 自举（mkfs）

**mkfs 不走位图分配** —— 位图还不存在。做法是「按策略直接算出位置 → 放好元数据 → 再把位图建起来」。

```
1. 已知 [start, len)，算出 data_lo / data_hi / 数据区字节数
2. 按 §3.4 选定 block_bytes，算出需要 K 个位图块
3. 按 policy（默认 middle-out）取一段连续空间放这 K 个块：
     - 连续放置 → 整张位图的顺序 IO 最好
     - 放好后按物理升序，依次绑定"区域 0 .. K-1"
4. 分配根目录的第一个 dir 块
5. 建位图：全清 0 → 把 anchor 区之外的已用块（K 个位图块 + 根 dir 块）置 1
6. flags.bit0 = clean，写这 K 个位图块
7. 写 head / tail anchor（tag：`peer` 互指、`allotype` = 1（扁平链）、`alloioff` → 区域 0 那块、`policy`、`chunk`、`allocnum` = K）
```

### 4.1 算例：1 GiB，默认 middle-out

| 项 | 值 |
|---|---|
| 数据区 | 1 GiB − 8 KiB = 262,142 个 chunk |
| 位图 | 每块 4000 B × 8 = 32,000 bit → **需要 9 块**（36 KiB）|
| 位置 | 以数据区中点（512.0 MiB）为中心的一段 **36 KiB 连续带**（511.98 – 512.02 MiB）|
| 根 dir 块 | 带后面紧跟的 1 个 chunk |
| 结果 | 中间 40 KiB 是永久元数据，**左右各约 512 MiB 空闲** |

### 4.2 永久元数据必须居中（比 `policy_id` 更重要）

位图块是**永久元数据**，永不释放；而缩容的前提是"那一侧 N 字节全空闲"。所以：

> **永久元数据（位图链、根 dir 块、bad 块表）必须居中，绝不能贴任一端，否则那一侧的收缩永久失败。**

反例：`first-fit-left` 会把位图块放在数据区最左端 → 左缩永久 `ENOTSUP`；
`random` 会两端都零星占住 → 两侧都容易失败。

| 对象 | 定位规则 |
|---|---|
| 位图链、根 dir 块、bad 块表 | **固定居中带**（与 `policy_id` 无关）|
| 文件数据块、子目录块 | 按 `policy_id` |

## 5. 分配策略

策略 id 存 anchor 的 tag `policy`（`mkfs` 时写入，运行时可用命令行覆盖）；随机种子 / 游标存 tag `polstate`。

| id | 名称 | 选哪一段 | 说明 |
|---|---|---|---|
| 0 | `first-fit-left` | 最左的空闲段，从左端切 | 紧凑向左 |
| 1 | `first-fit-right` | 最左的空闲段，从右端切 | |
| 2 | `last-fit` | 最右的空闲段 | |
| 3 | **`middle-out`** | 从数据区中点向两侧找 | **两端留空 → 左右伸缩最友好（默认）** |
| 4 | `best-fit` | 长度最接近需求的段 | 省大块 |
| 5 | `worst-fit` | 最长的段 | 大文件友好 |
| 6 | `random` | 带种子 PRNG 选段与位置 | 可复现（种子在 anchor 的 tag `polstate`） |
| 7 | `edge-reserve` | 两端各留 guard 段，其余按 id 0 | 保证收缩永远可行 |

**位图下这些策略都很好实现**：把位图当成 RAM 里的 bit 数组，策略 = 「选区域 + 选起点 + 选扫描方向」，
用 word 级扫描找连续 0。这也是选位图而不是空闲链表的根本原因 —— **空闲链表里没有"位置"概念，
「从中间往两边 / 随机」根本无从表达**。

### 5.1 策略与伸缩的耦合（重要）

收缩的充要条件是：**边界那 N 字节全部空闲，且从 `data_lo`（或 `data_hi`）起连续**。所以：

| 策略 | 左收缩 | 右收缩 |
|---|---|---|
| `middle-out` / `edge-reserve` | 容易 | 容易 |
| `first-fit-left` | 会失败（左端被填满） | 容易 |
| `last-fit` | 容易 | 会失败 |

注意：§4.2 的"永久元数据居中"已经把**元数据**这一层从这个问题里摘出去了；
上面这张表说的是**数据**填满边界时的情况。

## 6. 分配 / 释放算法

```
alloc(n_bytes, policy) -> (物理地址, 实际字节数) n_bits = ceil(n_bytes / bit_unit) 在位图 RAM 镜像里，按 policy 选区域与起点
  在该区域内扫 n_bits 个连续 0（word 级扫描）：
    找到   → 全部置 1，返回
    找不到 → 允许分裂时，返回该区域内最长的连续 0 段；否则 ENOSPC
  ⚠ 一次分配不跨区域

free(物理地址, n_bytes) 定位到块与 bit 范围（§2.2）→ 全部清 0
```

- 分配器只认**物理地址 + 长度**，不再有"相对 `data_lo` 的 chunk 序号"。
- 引用方（目录条目）自己换算成 delta：
  `DATA_PTR.offs = 物理地址 − 存放该 DATA_PTR 的那个块的起点`。

### 6.1 carve-out 规则

- anchor 区不属于任何区域，天然不会被分配。
- 位图链自身、所有已存在的 dir / link / bad 块，其 bit 恒为 1，**分配时不可能选中**。
- 任何"新增可分配空间"的操作（扩容）都必须把落在元数据块上的部分**挖掉**（置 1），
  不能让一个区域把正在使用的元数据块当成空闲。

### 6.2 扫描位图的开销（为什么按字节扫）

`alloc` 要枚举空闲段，也就是要扫位图。参考实现里 `free_runs()` **按字节扫**，
`0x00` / `0xFF` 整字节走快路径（只有段边界才逐 bit），`used_bits()` 用
`bytearray.translate` 做 C 级 popcount。实测（真实形态：空闲成段）：

| 卷大小 | 位图字节 | 一次全扫 | 极限碎片时 |
|---|---|---|---|
| 1 GiB | 32 KiB | 2 ms | 42 ms |
| 16 GiB | 512 KiB | 38 ms | 0.7 s |
| 256 GiB | 8 MiB | 0.6 s | 11 s |
| 1 TiB | 32 MiB | 2.4 s | 43 s |

- 逐 bit 调 `bit()` 要慢 **21 倍**（8M bit 扫 1.61 s vs 0.076 s）—— 这是实现层面的教训：
  位图方案的"word 级扫描"在 Python 里必须真的按字节/字做，否则等于没有。
- **≤16 GiB 每次分配都能接受**（≤40 ms，且一次写里只扫一遍：`alloc(runs=…)` 复用结果）。
  `free_bytes()` 同样是 O(位图字节) 的 C 级操作，所以目录页渲染不受影响。
- **≥256 GiB 需要"RAM 空闲段表"**（§14 第 7 条）或改用 C 实现。

## 7. 写顺序与崩溃一致性

### 7.1 两条纪律

| 动作 | 顺序 | 崩溃后的结果 |
|---|---|---|
| 占位 | **数据块 → 位图置 1 → dir 块引用** | 位图说已用但无人引用 = **泄漏**（安全，fsck 按补集回收） |
| 释放 | **dir 块解除引用 → 位图清 0** | 同上，泄漏 |
| ✗ 禁止 | dir 块先引用 → 位图后置位 | 位图说空闲但已被引用 = **双重分配**（互相覆盖数据） |

一句话：**先占位后引用；先解引用后释放。**

### 7.2 commit 模式

| 模式 | 位图何时落盘 | 后果 |
|---|---|---|
| `immediate` | 每次分配/释放都写"含该 bit 的那一页"（遵守 §7.1 顺序） | 磨损高；挂载时不需要重建 |
| `batched` | 只在 `flush` / `close` / `umount` 时写 | 磨损低几个数量级；**非正常卸载后的首次挂载必须全量重建位图** |

注意：**"写一页"而不是"写一整块"**。位图块可以到 1 MiB，但一次分配只改 1 个 bit，
只需重写那个 bit 所在的 `chunk_size`（4 KiB）页 —— 写成本与块大小无关（见 §10）。

### 7.3 clean / dirty 标志

放在 **head anchor 载荷里的 `flags.bit0`**（不是通用块头里的 `flags`）：

- 以读写方式挂载时先置 dirty（写 head anchor 一次），再动任何东西；
- `flush` / 正常卸载后置 clean（写一次）；
- 挂载时看到 dirty → **重建位图**（§7.4）。

放在 anchor 而不是位图块里的理由：挂载读的第一个块就是 anchor；而且位图**链头会随左右伸缩换块**，
标志放在链头会引入"换头时继承标志"的额外规则。代价是每次挂载/卸载各写一次 anchor
（NOR 上约 2 次擦写/会话，可接受）。

### 7.4 重建

```
rebuild():
  位图所有 bit 清零
  把 anchor 区之外的元数据块（位图链自身、所有 dir / link / bad 块）置 1
  从 anchor.Δroot 出发遍历：
      每个 DIR_PTR  → 子目录 dir 块链，整段置 1
      每个 DATA_PTR → 对应区间置 1
      每个 DATA_OBJECT → 链接块置 1
  统计 free_bytes
```

位图是派生数据，所以重建**永远安全**，代价只是一次全卷遍历。

### 7.5 位图数据的完整性（CRC 暂缓）

v0 **不给位图数据做 CRC**（`payload_crc32` 恒关，`flags.bit0` 保留；分段用的 `seg_bytes` 也先空着）。
这是可以的，但有一个**硬前提**：

> **§7.3 的 dirty + §7.4 的挂载时重建，必须真的实现。**
> 位图数据没有校验和，一次撕裂写入可能让已用的 bit 变回 0（→ 双重分配）。
> 唯一的安全网就是"非正常卸载后重建"。

通用块头的 `header_crc32`（只覆盖 64 B）保留 —— 它是 anchor / dir / link 共用的那一层，
不校验它的话，连"这个块是什么类型"都不能信。

## 8. 伸缩与位图

先记住：**只有缩容要求"边界空闲"；扩容不需要。**

### 8.1 本质

因为区域用**自相对 delta** 描述，伸缩只做两件事：

| 方向 | 动作 |
|---|---|
| 向右扩 | 为新区域**新建位图块**，**后插**到链尾；anchor 指向的链头不变 |
| 向左扩 | 为新区域**新建位图块**，**前插**到链头；anchor 改指新链头 |
| 向右缩 | 把最右的位图块**从链尾摘除**并释放 |
| 向左缩 | 把最左的位图块**从链头摘除**并释放 |
| 整卷平移 | **什么都不用做**（块和它管的区域一起搬，delta 不变） |

**已存在的位图块，一个字节都不用改；位图里的 bit，一个都不用挪。**
（这正是上一版"整张位图整体移位"被推翻的原因。）

> **本节导航**：调用方接口与前置检查见 **§8.6**；新位图块放哪见 **§8.7**；
> 撕裂状态与恢复见 **§8.8**。下面 §8.2~§8.5 先讲四个方向各做什么。

### 8.2 向右扩容（partition 先扩，再 adopt）

```
1. 分区表先扩大
2. 调用方告知新的 [start, len)
3. 计算新增区域 [old_data_hi, new_data_hi)，按 §3.4 切成若干区域，各建一个位图块
     region_delta = 各区域起点 − 块起点  （可正可负，取决于 §8.7 选的位置）
     region_bytes = 各区域字节数（最后一个可短）
     全部 bit = 0（空闲），但把落在元数据块上的部分置 1
     ⚠ 旧 tail anchor 占的那 4 KiB 正好落在新数据区的**起点**处（新数据区从旧 data_hi 开始）
       → 它的 bit 同样按新区域规则置 0（空闲），并且清掉它的 magic（见 §8.8 注）
4. 后插到链尾（原链尾的 next → 新块，新块的 prev → 原链尾）
5. 写 tail anchor 到新末尾、更新 head 的 peer_delta、region_len、allocnum
```

### 8.3 向左扩容（partition 起点左移）

```
1. 分区表先左移
2. 计算新增区域 [new_data_lo, old_data_lo)（自相对：在现有块左边）
3. 建位图块（位置按 §8.7 在新区域内选）：region_delta 为负（指向本块左边），
     region_bytes 按同样规则切，region_logical_start = 旧的 data_lo_logical − N + 各区域在新增区内的偏移
     全部 bit = 0（空闲）
     ⚠ 旧 head anchor 占的那 4 KiB 落在新区域内 → 它的 bit 也是 0（anchor 已搬走），并清掉它的 magic
4. 前插到链头（原链头的 prev → 新块；新块的 next → 原链头）
5. 写新 head anchor 到新起点：
     region_len += N、alloioff → 新链头、peer_delta 重算、
     **data_lo_logical −= N**（保证已有数据的 L 不变，见 layout.md）
6. 写 tail anchor（peer_delta 减 N 后为负数；data_lo_logical 同步更新）
```

**中间态安全性**（两个方向都是）：新块先建、anchor 后改 → 新区域还没进 `region_len`，
分配器碰不到它 → 安全；anchor 先改、新块后建 → 新区域的 bit 还没置，分配器看不到它 → 安全。
**不需要 dirty 事务。**

**两个注意点**：

1. **旧 head anchor 的槽位变成新区域里的一块**。那 4 KiB 里还留着旧 anchor 的内容，
   要更保险就在第 3 步顺手清掉它的 `magic`；不清也无害——`uuid + gen` 会忽略陈旧 anchor。
2. **N 必须是 `chunk_size` 的整数倍**（且 ≥ 1 个 chunk），否则 chunk 与物理地址的对齐关系被破坏。
3. **一次扩容不能跨区域**：新区域必须能被现有 `block_bytes` **整除成整数个区域**，
   否则最后一个区域会"短"，这时它的 `region_bytes` 小于容量 —— 合法。

### 8.4 收缩（两阶段：先腾空，再收缩）

收缩比扩容麻烦，因为**要缩掉的那段里可能有东西**。所以拆成两步：
**第一步把跨度腾空，第二步走"干净了就正常收缩"**。任何一步失败都**不改一个字节**。

**待缩跨度**：

| 方向 | 跨度 |
|---|---|
| 向右缩 N | `[new_data_hi, old_data_hi)`（旧的尾部）|
| 向左缩 N | `[old_data_lo, new_data_lo)`（旧的头部）|

**第一阶段：腾空**

```
1. 数跨度内的 bit：
     全是 0  → 直接进第二阶段
     有占用  → 逐个尝试挪走：
       · 位图块          → **挪**（v0 就挪这个，见下面"挪位图块"）
       · 文件数据块      → v0 不挪 → ENOTSUP
       · dir / link 块   → v0 不挪 → ENOTSUP
2. 报错时必须说清楚"什么东西挪不了"，实际长这样：

   ```
   ENOTSUP: 无法挪动 —— 待缩跨度里还占用 364.00 KiB（91 个 chunk）；
   位图块已挪走 1 个，剩下的是**文件数据或目录块**（v0 不挪）。
   先删掉/搬走占用边界的数据，或缩得少一点
   ```

   这些数量**从位图数 bit 就能得到**。注意 v0 **区分不出**"文件数据"和"目录块"
   —— 那需要扫整棵目录树（正是"挪数据"才要做的事），所以合并成一句报。
   （**根目录块也算在"目录块"里**，所以卷缩到根目录块所在的位置会被拒绝。）
3. 腾空后自检：跨度内所有 bit 必须为 0，否则拒绝
```

**挪位图块**（纯元数据搬运，不需要知道"谁引用了它"—— 链和 anchor 就是全部引用）：

```
1. 在**保留区**里按 §8.7 的策略找一段 block_bytes 连续空闲；找不到 → ENOTSUP
2. 整块内容拷到新位置，重算 region_delta（它相对自己位置，块动了就得重算）
3. 改邻居的 prev_delta / next_delta（链头/链尾时改 anchor.alloioff）
4. 把旧位置的 bit 清 0；新位置已经是元数据，bit 保持 1
5. 必须在改 anchor（第二阶段）之前全部完成
```

**第二阶段：干净了，走正常收缩**

```
向右收缩 N：
  1. 最右区域的 region_bytes -= 剩余 N（若整块变空则从链尾摘除并释放）
  2. 写 tail anchor 到新末尾，region_len -= N
  3. 清掉离开卷的那个 anchor slot 的 magic（右缩的旧 tail）
  4. 分区表最后收缩（外部的事，见 §8.6）

向左收缩 N：与 §8.3 对称 —— 最左区域的 region_bytes -= N（整块变空则摘除链头块），
  并同步 **data_lo_logical += N**（保证已有数据的 `L` 不变，见 [`layout.md`](layout.md)），
  写新 head anchor，清掉旧 head slot 的 magic

N 超过最外区域的 region_bytes 时**循环**处理：可能连摘多个块，直到 N 用完。
```

**摘除一个区域块时，它自己的 chunk 谁来释放**（这条不写清楚会漏回收或误报 ENOTSUP）：

| 该块的物理位置 | 怎么做 |
|---|---|
| **在**待删跨度内 | 它随区域一起消失，**允许它的 bit 为 1**（这是"跨度内必须全 0"的唯一例外），不用额外清 |
| **不在**待删跨度内（**常态**：mkfs 把链放在数据区中间，每块基本不在自己管的区域里）| 必须在**覆盖它的那个保留区域**的位图里清掉它的 bit，这块要重写一次 |

**收缩失败**：腾空阶段遇到搬不走的东西，或保留区没有连续空间 → `ENOTSUP`（此时**还没写任何东西**）；
调用方给的几何非法 → `EINVAL`；anchor 不一致或 I7′ 不成立 → `ESTALE`。v0 不做在线 defrag。

| 卷大小 | 块大小 | 左扩 1 GiB 需要新增 | 成本 |

调用方必须给出**旧几何**和**新几何**两组数，缺一不可 —— 因为卷里**不存自己的起点**，
"旧位置在哪"只有调用方知道（容器里真正的位置可能是文件内的某个偏移）：

```
```
省略规则：`--offs`/`--size` 都不给 = 整个文件；`--newoffs` 省略 = 与 `--offs` 相同；
`--newsize` 省略 = 到容器末尾。`--mode` 给了就当**断言**校验（与几何不符即 `EINVAL`）。
`--dry-run` 只推导 + 检查 + 打印计划（0 次写）；`-v` 打印步骤与**写入序列**；
收尾默认跑自检（I7′ + 位图与可达集合比对），`--no-verify` 可关。

**写入顺序**（`-v` 里能看到）：

1. 扩容：先清掉**旧 anchor 槽位的 magic**（它就落在新数据区里），再写新位图块，最后两个 anchor；
2. 收缩：先写位图块（腾空 + 截短/摘除），再写两个 anchor，最后清掉**离场 anchor 槽位的 magic**。

位图块永远在 anchor 之前 —— 这样任何时刻崩溃都不会出现"anchor 说区域更大，但位图还没跟上"。

**方向由几何唯一确定**，不用问也不用猜：

| 新旧关系 | 方向 |
|---|---|
| `S₁ = S₀`，`L₁ > L₀` | `expandright` |
| `S₁ + L₁ = S₀ + L₀`，`L₁ > L₀` | `expandleft` |
| `S₁ = S₀`，`L₁ < L₀` | `shrinkright` |
| `S₁ + L₁ = S₀ + L₀`，`L₁ < L₀` | `shrinkleft` |
| `S₁ = S₀`，`L₁ = L₀` | 无需操作（幂等：直接返回）|
| 其它（两端都动了）| `EINVAL`，提示"分两步做"（先扩一边再扩另一边）|

**约束**：`S₁` 与 `L₁` 必须是 `chunk_size` 的整数倍（否则 `data_lo = S₁ + 4096` 与 chunk 的对齐被破坏）；
`[S₁, S₁+L₁)` 必须落在容器内。

**两条只读前置检查**（任一不过即拒绝，一个字节都不改）：

| 检查 | 不过时 | 为什么 |
|---|---|---|
| head/tail 关键字段一致（**I9**）| `ESTALE` | 可能是没做完的 resize，也可能是 `--offs/--size` 给错了 |
| **I7**：位图链并集 == `[data_lo, data_hi)` | `ESTALE` | 链比 `region_len` 长 → 分配器会写到卷边界外；短 → 丢空间。两种都只来自"没做完的 resize" |
（该动作只推导 + 检查 + 打印计划，**0 次写** ✓。）
**容器（分区表 / 镜像文件大小）不是本模块的事**，本模块只改区域内部的字节：

- **扩容**：调用方要**先**把容器弄大（否则新区域落在容器外，早期就报错）；
- **缩容**：本模块**先**缩卷，调用方**后**缩容器 —— 反了会让 tail anchor 读不到。

### 8.7 新位图块放在哪：按当前策略，在新区域里选

新建的位图块**不是**固定在区域头尾，而是**按当前分配策略在"它自己管的那个新区域"里选址**：

| 策略 | 落点 |
|---|---|
| `middle-out` | 新区域的**中点** |
| `first-fit-left` | 新区域最左的空闲 chunk |
| `first-fit-right` / `last-fit` | 新区域最右 |
| `random` | 新区域内随机（种子取自 `policy_state`，可复现）|
| `best-fit` / `worst-fit` | 退化为最左（整段都是空闲，无差别）|
| `edge-reserve` | 按 0 号选，但避开区域两端的 guard 段 |

要点：

- 每个新区域各放一块；`block_bytes` 沿用现有值；最后一个区域可以短。
- 落在元数据块上的 bit 置 1，其余 0。
- **别贴边**（同 §4.2 的理由）：贴边会让后续收缩立刻撞上，等于自己堵死伸缩。
- **实现上不能复用 `alloc()`** —— 新区域此刻还没进位图（鸡生蛋）。需要一个独立函数，
  把新区域当作"一整段空闲"，按上表选点（`place_metadata`）。

### 8.8 撕裂状态与恢复

**凡是"链/anchor 自己记的"与"调用方说的"可能不一致的地方，一律以卷自己记的为准，不一致就报错。**
撕裂只可能来自"写了一半"，具体就三种，两条只读检查刚好全覆盖：

| 撕裂点 | head/tail 一致（I9）| I7′ 成立 | 谁发现 |
|---|---|---|---|
| 扩：新位图块已入链，anchor 还没改 | 一致（都还是旧的）| ✗ 根区域并集比 `region_len` **长** | I7 |
| 缩：位图已裁，anchor 还没改 | 一致（都还是旧的）| ✗ 根区域并集比 `region_len` **短** | I7 |
| 只写了一个 anchor | ✗ 不一致 | 成立 | I9 |

两种 I7′ 不成立的状态都是**有害**的（分配器会落到 `data_hi` 之外，或丢掉尾部空间），
所以不是"只警告"。

**恢复办法**：不提供 `--fix`、不猜。用 `probe` 看两个 anchor 与 I7′ 判定，然后
**换另一组几何重试**（撕裂时另一组几何就是完整的那个：左类操作按新几何能挂上，
右类操作按新几何也能挂上）。然后重跑 resize 即可；未引用的新区域被当作泄漏，
下次重建位图时回收。

**关于旧 anchor 槽位的 magic**：离开卷的那个 slot（右扩的旧 tail、左扩/左缩/右缩移走的那个）
里面还留着"看起来完全合法"的 anchor。**清掉它的 magic** 让"按旧几何挂载"直接失败、
而不是静默挂上一个大小不对的卷。这不是兼容性问题，是**防手滑**：同一个命令复制过来重跑，
或者脚本里写死了旧的 `--offs/--size`，就会撞上这个 slot。

## 10. 磨损

位图是**唯一会被高频重写**的元数据。以 ESP32 内部 NOR（4 KiB 扇区、约 10 万次擦写）为例：

| 位图写法 | 单扇区寿命 |
|---|---|
| `immediate`，1 次/秒 | ≈ **28 小时** |
| `immediate`，1 次/10 秒 | ≈ 11.5 天 |
| `batched`（只在 close/flush/umount） | 提升几个数量级 |

**两点和上一版不同：**

1. **块大小不影响写入成本**：一次分配只重写"含那个 bit 的 4 KiB 页"（§7.2），
   所以 1 MiB 的位图块不会让每次分配变成写 1 MiB。代价是"一个块被拆成多个独立的 4 KiB 页写入"，
   而没有页级校验和保护 —— 所以 §7.3 的 dirty + §7.4 的重建是必须的。
2. **位图块的写入天然分散**：每块只被它自己那片区域（1 MiB 块 → 32 GiB）的分配触及，
   块越大越分散。但分布仍取决于策略：`random` 最均匀，`middle-out` 初期集中在中间那 1~2 块。

**结论**：`commit_mode` 是数量级杠杆；块大小是线性/分布杠杆。

## 11. fsck 检查清单（分配层）

1. 每个位图块的 `header_crc32`；`block_type == 1`。
2. 字段自洽（§3.3）：`block_bytes == header_bytes + payload_len`；
   `有效 bit 数 ≤ 可用 bit 数`；`region_bytes` 与 bit 数匹配。
3. `block_bytes` 是 `chunk_size` 的整数倍；`bit_unit` 是 `chunk_size` 的整数倍且为 2 的幂
   （v0 必须 `== chunk_size`）；`region_bytes` 是 `bit_unit` 的整数倍（末区例外）。
4. **区域 tiling**：按 `region_delta` 算出各区域的物理区间，必须**首尾相接、无洞、无重叠**，
   并集 = `[data_lo, data_hi)`；任何区域都不得覆盖 anchor 区。
   —— 这条（= I7′，§13.7）**挂载时和每次 resize 前都要跑**，不成立即拒绝（`ESTALE`，见 §8.8）。
5. 链上 `prev/next` 互指一致、无环；`seq` 沿链严格递增；链长 == `anchor.allocnum`；
   `Σ block_bytes == anchor.allosize`。
6. 位图链自身、所有 dir / link / bad 块对应的 bit 必须为 1。
7. 从根遍历出的所有可达块（dir / link / 裸数据块）对应的 bit 必须为 1。
8. **bit 为 1 但不可达** → 泄漏，清 0 回收。
9. **bit 为 0 但可达** → **危险（双重分配风险）** → 报错，并按 `DATA_PTR` / `DATA_OBJECT` 重新置 1。
10. `region_bytes` 之外的"多余 bit"必须为 0（或忽略，但不得被分配）。
11. **物理侧与逻辑侧必须一致（I8）**：
    `block_addr + region_delta == data_lo + (region_logical_start − data_lo_logical)`；
    且各块的 L 区间必须无缝铺满 `[data_lo_logical, data_lo_logical + (data_hi − data_lo))`。

## 12. 上限与错误码

| 项 | 值 |
|---|---|
| `chunk_size` | 默认 4096，可配 512 / 1024 / 2048 / 4096（**v0 上限 4096**，见 [`layout.md`](layout.md)） |
| `bit_unit` | 2 的幂，≥ `chunk_size`；**v0 恒 == `chunk_size`** |
| `block_bytes` | 4096 … 4 GiB−1（u32），必须是 `chunk_size` 的整数倍 |
| `header_bytes` | 位图块 ≥ 96；其它类型恒 64；8 的倍数且 < `block_bytes` |
| 单个位图块覆盖 | `payload_len × 8 × bit_unit`（4 KiB 块 + 4 KiB unit = 125 MiB；1 MiB 块 = 32 GiB）|
| 位图链长 | `ceil(数据区 / 单块覆盖)`（1 TiB + 64 KiB 块 = 513；16 TB + 1 MiB 块 = 513）|
| 单次分配长度 | ≤ 一个区域内的最长空闲段（**不可跨区域**） |
| 伸缩粒度 | `chunk_size` 的整数倍，≥ 1 个 chunk |

| 错误码 | 含义 |
|---|---|
| `ENOSPC` | **真没空间**：找不到足够的连续空闲 |
| `EFRAG` | **有空间但太碎**：段数超过**写侧 v0** 的单条目上限（格式允许条目跨块续段），见 [`2-dir.md`](2-dir.md) |
| `ENOTSUP` | 需要 compaction 才能收缩（待缩跨度里有搬不走的东西、或保留区没有连续空间）；或写空洞（`offset > size`） |
| `EINVAL` | 长度/对齐/参数非法；容器比卷小；两端同时动 |
| `EIO` | 设备读写失败 |
| `EDIRTY` | 位图 dirty，需要先重建 |
| `ESTALE` | **卷记的与调用方说的不一致**：head/tail 关键字段不一致（I9），或位图链与 `region_len` 对不上（I7）。只可能是"上次 resize 没做完"或"`--offs/--size` 给错了" —— **拒绝操作，不许猜**（§8.8） |

> `ENOSPC` 与 `EFRAG` 必须分开报：前者是"卷满了"，后者是"卷还有 N MiB，但最大的连续段
> 只有 M KiB"。混成一句"空间不够或碎片太多"会让人对着 `df` 发呆。

## 13. 混合粒度：粗粒度起步 + 按需分裂
> **默认策略**：不给参数就自动选型（§13.3）；格式始终是"位图链 + 每块自带 `bit_unit`" ✓，所以平铺卷与混合卷可以互相挂载 / `migrate` ✓；`mkfs --fixbitsize 4K|64K|1M|…` 可强制"1 bit = 多少字节"（2 的幂、`chunk` 的整数倍 ✓），其中 `--fixbitsize 4K` 正好复现**旧的平铺布局**（1 TiB = 513 块 / 32 MiB ✓）。
> **`resize` 四个方向**：左扩 / 左缩 / 右扩 / 右缩 ✓。
> **整理不自动做**（§13.6）；`resize` 扩出来的新空间按 `chunk` 粒度 ✓
>

### 13.1 目标

**起步时只用"一个 4 KiB 位图块"，让它尽量覆盖整个卷**；只有真需要细粒度时才分裂出子位图。
1 TiB 对比：

| 方案 | `bit_unit` | 位图元数据 | 一个 bit 管 |
|---|---|---|---|
| 现在（§3.4 自动放大位图块）| 4 KiB | **32 MiB**（64 KiB × 513）| 一个数据块 |
| §13（单个 4 KiB 块）| **64 MiB** | **4 KiB** | 16384 个数据块 |
| 分裂之后 | 4 KiB（**只在那一片**）| 按需 +4 KiB/片 | 一个数据块 |

⇒ 元数据降 ~8000×；`alloc` 要扫的 bit 数同降（§6.2 的性能瓶颈）。

### 13.2 模型与**父子关系怎么表达**

* **区域**：一个位图块管的一片空间 + 它的 `bit_unit`（§3.2 已有的字段）
* **分裂**：把一个 `bit_unit = U` 的**单位**（连续空间 `[P, P+U)`）交给一个**新区域**管；
  父位图里那一位标为**已用**（= "已分裂到下一级"）
* **合并**：子区域全空 ⇒ 删掉它、清父位图那一位（**本期不做**，见 §13.5）

**父子关系不加新字段，靠"包含"推导**：

* 链仍然是**一条按 `logical_start` 从小到大排的链**（现状就是这样，`prev_delta`/`next_delta` 串起来）
* 定义：`B 是 A 的子区域 ⇔ A.start ≤ B.start 且 B.end ≤ A.end 且 B ≠ A`
  ⇒ **父 = 严格包含它的最小区域**（由"同层不重叠"保证这个父唯一）
* 于是链里天然是"父在前、子在后"（父的 start ≤ 子的 start），大中小混在一条链上 —— 这正是现在的形态
* 挂载时把链读进 RAM，按 `start` 排一遍（块数很小，1 TiB 起步只有 1 块），
  就能 O(log n) 答"某个地址落在哪个**叶**区域里"（叶 = 没有子区域的区域）
* 备选（**不采用**）：在 32 B 扩展之后再放一个 `parent_delta`（把 `header_bytes` 抬到 112）
  ⇒ 换来 O(1) 查父，代价是每块少 128 bit 容量 + 多一个要维护的字段。包含推导够用。

### 13.3 起始粒度 `bit_unit0`：一个 4 KiB 块尽量多覆盖

一个 4 KiB 位图块的位图载荷 = `(4096 − 96)` **字节** = 4000 × 8 = **32000 bit**。
⇒ `bit_unit0` = **最小的 2 的幂，使 `ceil(region_bytes / bit_unit0) ≤ 32000`**（且 ≥ `chunk`）：

| 卷大小 | `bit_unit0` | 用掉的 bit | 位图块 |
|---|---|---|---|
| 64 MiB | 4 KiB（= `chunk`，不用变粗）| 16384 | 1 |
| 1 GiB | 64 KiB | 16384 | 1 |
| 200 GiB | 8 MiB | 25600 | 1 |
| 1 TiB | 64 MiB | 16384 | 1 |
| 4000 GB | 256 MiB | 16000 | 1 |
| 16 TiB | 1 GiB | 16384 | 1 |

* `bit_unit` 的阶梯：`4K / 8K / 16K / … / 1M / … / 256M / 1G`（**每次 ×2**，2 的幂）
* 注意 **4000 是字节不是 bit**：4000 GB 用满 32000 bit 是 **256 MiB/bit**（≈131 MB 取整到 2 的幂）；
  若按"4000 bit"算成 1 GB/bit，等于白白浪费 7/8 的位图空间。
* 起步**恒为 1 个 4 KiB 位图块**（不再靠"放大 `block_bytes`"去凑 ≤1024 块，§3.4 的规则被 §13 取代）

### 13.4 分裂规则

要把一个单位 `[P, P+U)`（父的 `bit_unit = U`）细分到 `chunk`（4 KiB）：

* 子区域覆盖 `U`、`bit_unit' = chunk` ⇒ 需要 `U / chunk` 个 bit
* **优先一步到位**：给子区域一个更大的位图块 —— `block_bytes'` 从 4 KiB 起 ×2，
  取第一个满足 `(block_bytes' − 96) × 8 × chunk ≥ U` 的值（**和 §3.4 的阶梯同一个套路**）
  * 例：`U = 4 MiB` ⇒ 1024 bit ⇒ 4 KiB 块就够 ✓；`U = 1 GiB` ⇒ 262144 bit ⇒ 需要 32 KiB 块 ✓
* 若 `block_bytes'` 会超过上限（4 GiB ⇒ 一块覆盖 128 TiB @4 KiB）⇒ 那一级改放**多个同级块**
  （就是 §8.7 那套"一块覆盖一段、按顺序接上"的做法，区域字段天然支持）
* ⇒ **树上基本只有两层**（父 + 一层到 4 KiB 的子）

**触发条件：只要请求小于当前区域的 `bit_unit`，就直接分裂** —— 不搞"再去别处凑一个粗单位"。
现实就是：文件大小**除了刚好等于粗单位**，多一字节少一字节都要细粒度 ⇒ 分裂是常态，不是例外。

**一次分裂，长期受益（成本上界）**：分裂出来的子区域 `bit_unit = chunk`，
它自己就能吸收后续所有落在这片里的小分配（`U/chunk` 个槽位）。
⇒ **分裂次数 ≈ 「小文件总字节数 ÷ U」**，而不是"小文件个数"：

| 场景（`U` = 64 MiB）| 小文件总量 | 最多分裂几片 | 子位图元数据 |
|---|---|---|---|
| 1 万个 4 KiB 文件 | 40 MiB | **1 片** | 4 KiB |
| 10 万个 100 KiB 文件 | 10 GiB | 160 片 | 640 KiB |
| 极端：1 TiB 全是小文件 | 1 TiB | 16384 片 | 64 MiB |

⇒ 元数据 ≈ `小文件字节数 / U × 子块大小`，**与文件个数无关** ✓

### 13.5 自举：mkfs 必须先把"元数据那一片"分裂到 4 KiB

如果 mkfs 只建一个粗区域，那么 4 KiB 的位图块和根目录块会**各自吃掉一整个粗单位**：
1 TiB 用 64 MiB 单位 ⇒ 元数据白占 **128 MiB**，比 §13.1 省下的 32 MiB 还多 ✗。
⇒ mkfs 的流程必须是：

1. 按 §13.3 算出 `bit_unit0`，建**一个**粗区域（`allocnum = 1`）
2. **立刻把那一个"要放元数据的单位"分裂成 `chunk` 粒度**（子区域，§13.4 的做法）
3. 位图链自己 + 根目录块都从**这个子区域**里分配（于是它们各占 4 KiB 而不是一个粗单位）

⇒ 起步是 `allocnum = 2`（粗 1 + 子 1）＝ **8 KiB 元数据**（1 TiB 从 32 MiB 降到 8 KiB ✓）。

**摆放规则：一个 bit（单位）里只放"一类可独立挪动的对象"** ✓：

* **分配块占一个单位**（子位图块 + 粗位图块）、**根目录块占另一个单位** —— 目录块和分配块
  **绝不共用同一个 bit**
* 为什么必须这样：两块都各自可能被挪动 / 回收。若共用一个 bit，清这个 bit 时只有三种结局：

  | 做法 | 后果 |
  |---|---|
  | 以为自己是最后一个、提前清掉 | ✗✗ **静默双占用**：别人还在用的空间被标空闲 ⇒ 分配器再发出去 ⇒ 双方写同一片字节，**当时不报错**，很久以后才炸 |
  | 发现有别人占着就不清 | ✗ **永久泄漏**：安全，但这一格永远收不回（本文件早期的自举就是这个状态）|
  | 等最后一个占用者清完再清 | ✓ 正确，但**必须知道"还有几个占用者"** ⇒ 需要引用计数 |

* **本设计选"禁止共享"** ✓，于是"还有没有别人占着"**不需要引用计数** —— 用结构就能判定：
  1. 粗区域里一个**已用 bit** 的归属者只可能是"**一个子区域**"（已分裂 ⇒ 查父子表即知）
     或"**一段直接分配出去的数据**"（查子区域表：没有子区域落在这一格 ⇒ 是数据）；
  2. 子区域里每个 bit = 一个 `chunk` ⇒ 天然一主；
  3. **部分重叠**（一格既装子区域的一部分、又装别的东西）⇒ 直接判非法。
* 代价：**偶尔浪费**（两个相安无事的小块不能挤在同一个粗 bit 里）—— 换来的是回收语义永远清楚 ✓。

**实现成三条硬规则（都由 `check_regions()` 在挂载时检查，违反即 `ESTALE`）**：

1. **子区域按整单位对齐**：从父区域的单位边界开始、到单位边界结束（可以跨多个单位，
   但**不能占半格**）；
2. **子位图块住在子区域自己的第一个单位里**，并在**子区域自己的位图**里把这前几格标成已用
   —— 它属于这个子区域，跟着子区域一起生灭 ⇒ 绝不会和"别人"挤在同一格；
3. **回收判定 = "除自己的位图块外没有别的已用格"**：`optimize alloc` 就按这条判断能不能合并
   （比"全空"更准 —— 子区域永远带着自己的位图块）。

### 13.6 显式整理（不自动做）
分裂/追加这类操作都是"**只用不还**"的：分裂出来的子区域、被 `PADn` 撑开的目录块、
被拆成多段的 `DATA_PTR` —— 用完不会自己缩回去。**删掉东西不会自动回收元数据**，
所以整理做成**显式命令**（自动合并的问题：链会频繁增删块 ⇒ 元数据写变多，判断本身也费扫描）。
**共同纪律**（每个子命令都要守）：

1. **只动元数据，不动可见内容**：`optimize` 成功与否，读出来的目录树、文件内容、时间戳都不变 ✓
2. **一个一个来**：每项单独"改引用 → 释放旧的"，崩在半路只会**少整理几个**或**留下一个空壳**，不会损坏 ✓
3. **先验证后动手**：跑之前要求卷是干净的（`fsck` 过），运行结束再自检一次 ✓
4. **先看后做**：整理动作要能**只推导**"能回收多少块 / 多少字节"而不动盘 ✓

### 13.7 不变量怎么改（I7 → I7′）

原 I7 是**平铺**说法（§2 最后一条）：链上各区域首尾相接、无洞无重叠、并集 = `[data_lo, data_hi)`。
分层之后改成：

0. **一个 bit 一主**：每个**已用 bit** 的跨度里只有一个归属者；粗 bit ⇔ 整格交给一个子区域
   或整段直接分配；子区域里每个 bit ⇔ 一个 `chunk`；**出现部分重叠即报错**（§13.5）
1. **链按 `logical_start` 递增**（这条现在也成立，混合粒度下仍然成立）
2. **同一层**（同父之下的兄弟，含根层）区域之间**首尾相接、无洞无重叠**
3. **子区域**必须完全落在父区域的**某一个单位**内，且父位图里那一位是**已用**（= 已分裂）
4. **叶区域**的并集 = `[data_lo, data_hi)`
5. 父区域里"已分裂"的单位**不计入父区域的空闲** ⇒ `df` 天然不重复计数

fsck（§11）相应扩成：父子包含关系、每层无缝无重叠、叶子覆盖完整、`bit_unit` 整除链。

### 13.8 落地状态

| 位置 | 状态 |
|---|---|
| 位图单元粒度上限 | 约束 = **2 的幂** + `chunk` 的整数倍（不再另外限死数值）|
| `plan_layout` / `mkfs` | ✓ 已改：默认自动选型；`--fixbitsize` 强制粒度 |
| 区域元组 | ✓ 已是 `(起点, 字节数, bit_unit, 块大小, 块位置)`；两个分支返回的键**完全一致** |
| 父子 / 叶索引 | ✓ `_build_tree()` 按"包含"推导；`leaf_of_phys()` |
| 分配器 `alloc` | ✓ 请求 < 粗单位就**分裂一次并直接用新子区域**；小块**优先落在已细粒度化的区域** |
| `_walk_used` / `df` | ✓ 按各区域自己的 `bit_unit`；空闲按**所有区域**求和（父的已分裂单位不计） |
| fsck / 挂载检查 | ✓ I7 → I7′（根平铺 + 子包含 + 链按 start 递增）；每层无缝 / 叶覆盖的细查**未加** |
| `commit()` | ✓ 会重写 anchor 的 `allocnum` / `allosize`，并让 `gen` **+1** |

### 13.9 已定的选择

1. **分裂触发**：请求 < 当前区域 `bit_unit` 就**直接分裂**（不去别处凑粗单位）—— §13.4
2. **子位图块放哪**：按当前策略选址，默认 `middle-out` ⇒ **从卷中心向两边扩展**，
   和 §4.2"永久元数据必须居中"同一个理由：**两头 shrink 都便宜**
3. **整理**：不自动，做成一个显式触发的整理动作（§13.6）
