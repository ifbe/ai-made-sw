# 用 EasyFS 做内存管理（讨论结论）

> 状态：**讨论记录 / 设计笔记**，不是规格。基于当前定稿的格式
> （块类型 `0`–`6`、`block_type=3` 链接块、目录链续段、`PADn`/`PAD1` 占位，
> 见 [`common.md`](common.md) 与 [`2-dir.md`](2-dir.md)）。
>
> **一句话结论**：值得借的是**分配层**（位图 + 区域描述符 + 放置策略）；
> 不值得借的是**文件层**（目录、条目、块头、CRC、提交顺序）。
> 数据面交给 MMU，EasyFS 只在控制面出现。
>
> ⚠️ 本文里的数字与结论都基于 v0 格式；标"决策"的是已经落到格式里的东西。

---

## 1. 先分清三种问法（结论完全不同）

| 问法 | 结论 |
|---|---|
| **(a)** 把 RAM 当块设备，在上面跑一个 EasyFS 卷（RAM disk / 持久对象存储 / 崩溃转储区）| **可行**。格式层面没问题，16 GiB 下元数据开销 0.0031% |
| **(b)** 借它的**分配层**当物理页框 / 区域分配器 | **半可行**：形状对得上一半，缺的东西在 §9 |
| **(c)** 当 `malloc` 替代品 / 通用内核分配器 | **不行** —— 不是"慢一点"，是形状不对（§7）|

---

## 2. 规模与开销：16 GiB 的实际数字

```
16 GiB / 4 KiB chunk      = 4,194,304 个 chunk    → 4,194,304 bit
位图本体                   = 512 KiB（4 Mi bit / 8）
按自动选型（块数 ≤ 1024）  = 132 个 4 KiB 位图块 = 528 KiB（含块头，1-alloc.md）
                          = 全部内存的 0.0031%
```

* `chunk ≤ 4096` 的 v0 约束在内存场景下正好合适：**1 bit / 4 KiB 页**，与经典页框位图分配器同构。
* 位图块的 `block_bytes` 自适应（4 KiB…4 GiB），16 GiB 时选 4 KiB / 132 块，远低于 1024 块上限。
* `L` 是 `i64`，16 GiB 的地址空间完全不吃紧。
* **结论：位图这一层不是问题**，开销小到可以忽略。问题全在"位的上面那一层"。

---

## 3. 推荐的形态：两级分配（决策）

```
┌─ 区级分配器：EasyFS 分配层（1-alloc.md）+ 命名 + 策略 + 区属性      ← 慢，但很少动
│    分配单位 = 区（2 MiB / 64 MiB 量级），一个区 = 一个"文件条目"
│    职责：命名、放置策略、属性（DMA / 不可缓存 / NUMA）、两端伸缩、持久化
├─ 区内小分配器：buddy / slab / free-list（格式之外，元数据在区内部） ← 快，随便动
└─ 数据面：MMU 直接把区的物理段表装进页表，之后读写不经过 EasyFS
```

| 要点 | 为什么 |
|---|---|
| **区是 FS 的最小对象**，不要一页一个条目 | 4 KiB 一对象的话 16 GiB 要 4M 个条目，目录本身变成索引结构，而目录是**线性扫**的 |
| 区数控制在**几百 ~ 几千** | 区表可常驻内存：反查、策略、诊断都是 O(#区) |
| 小分配器的元数据放在**区内部** | EasyFS 只认"这个区整体归谁"，不认区里怎么切；删区 = 整区回收 |
| 需要 `align` 参数（如 `alloc(nbytes, align=2MiB)`）| 现在分配器只按策略选段、**不保证对齐**；大页 / DMA 必须对齐。这是接口层要加的，不动格式 |
| 需要**区属性** | 只有 1 bit 表达不了"这块不能给 DMA"。用属性扩展段（`0x60+`）挂 `区属性{cacheable/dma/nodes}` 即可，格式不用改 |

**代价**：

1. **两级碎片耦合**：小分配器碎到无法归还 → 大分配器看不到那些空间。要么小分配器支持"区空即还"，
   要么接受"区一旦给出就长期被占"，但必须能统计"区内浪费率"。
2. **大块请求会失败而总量够**：没有在线 defrag（[`proscons.md`](proscons.md) C8），要"连续 2 MiB 且对齐"
   可能失败。内存管理比文件系统更怕这个（DMA / 页表 / huge page 都要物理连续）→ 只能靠**预留池 + 区属性**绕过。
3. **区级写放大**（仅持久化时）：改一个 bit 要重写整块位图（持久路径，见 §5）。

## 4. 反查：地址 → 谁（决策：全部放在格式之外）

| 级别 | 做法 | 成本 |
|---|---|---|
| **区 → 谁** | 挂载时把区表读进内存，按物理地址排序，反查二分 | 16 GiB / 2 MiB 区 = **8192 个区** → 表 64~256 KB，可忽略 |
| **区内页 → 谁** | 小分配器自己的元数据（buddy 的 free 树 / slab 的页描述符）**本来就是反查** | 0（本来就要维护）|
| **任意地址 → 谁**（诊断 / 取证）| 上面两级拼起来；再不行离线扫全树 | 只在诊断时付 |

EasyFS 天生给的是**正向映射**（区 → 物理段表），而正向映射**可逆**，且区数很少 →
在内存里反转一次就行，**不需要往盘上写任何东西**。

这正是 [`proscons.md`](proscons.md) **P4（位图是纯派生数据）**的价值：
**它给了"在 RAM 里随便加加速结构"的许可证** —— 汇总位图（bitmap-of-bitmaps）、空闲段表、
分配游标、per-CPU 位图，全都是派生数据，坏了重算即可，**不改格式**。
反查表同理：它是派生结构，不是第二份真相。

## 5. 纯易失 RAM 下：什么该扔、什么该留

**先澄清一个容易搞错的点**：

| 场景 | 改一个 bit 的代价 |
|---|---|
| **纯易失 RAM**（"设备"就是内存本身）| **就是翻一个 bit**（位图是常驻内存的 bytearray）。没有设备写、没有 CRC、没有提交顺序、没有 dirty 重建 |
| **设备后端**（SD / NOR / 文件 / 持久内存）| 要落盘就得写整块：块是 I/O 单位也是 CRC 单位，没有"写一个字节"的路径 |

所以"每次分配要重写 4 KiB 元数据块"这类说法**只对持久路径成立**。纯 RAM 下，
块头 / CRC / 提交顺序 / dirty 位 / 挂载重建**全是死重量，应该整体扔掉**。

| 该扔（纯 RAM 下）| 该留 |
|---|---|
| 64 B 通用块头、`header_crc32` / `payload_crc32` | **1 bit / chunk 的位图语义** |
| 提交点 / 写序纪律 / dirty + 重建 | **自描述区域描述符**（每块声明自己管哪片）+ 有序链 |
| 位图"块"这个概念本身（直接是 RAM 数组）| **放置策略集合**（middle-out / edge-reserve / first-fit-left …）|
| 两端伸缩、`L` 坐标（物理地址搬不走）| **区属性 / 命名**（控制面需要）|

**RAM 里真正的热路径成本只有两个**：

1. **找空闲段**（不是写）：朴素扫位图是 O(位图)。16 GiB 约 4 Mi bit，
   字节快扫（[`1-alloc.md`](1-alloc.md)）大约几毫秒级 —— 对分配器仍然太慢
   → 必须加**汇总位图 / 空闲段表 / 游标**（派生数据，允许加）。
2. **对象绑定**：如果坚持"每次分配 = 一个目录条目"，那条目所在块的读改写才会成为成本
   —— §3 的两级分层正是为了躲开它。

## 6. 链接机制在内存场景里的作用（决策）

| 机制 | 内存场景里的用处 |
|---|---|
| **硬链接**（[`3-link.md`](3-link.md)：链接块 = `NLINK` + 时间 + 文件位置；条目 = `NAME + DATA_OBJECT{L}`）| **共享 + 引用计数**：多个"名字"共享同一片内存（DMA 池、共享缓冲区、COW 的物理页组）。`NLINK` 只在链接块里，目录条目里没有；归零才释放 |
| **软链接**（`SYMLINK_TINY` / `SYMLINK_PTR` / `SYMLINK_OBJECT`，与内容编码 ①②③ 对应）| 纯名字空间的别名，内存管理基本用不上；但可以用来登记"这块内存是干什么的" |
| 不允许 | 硬链接到**目录**（我们的路径解析把"目录是树"当前提）、硬链接到**软链接**（创建时 `ENOTSUP`）|

**注意**：链接块给出的是"**计数 + 位置**"，不是"引用计数式的页共享" ——
内核里的共享页还要 COW、反向映射、迁移，这些都没有（§9）。

## 7. 为什么不能当通用页框 / malloc 分配器（硬伤清单）

| 内核内存管理的需求 | EasyFS 的现状 |
|---|---|
| O(1) / O(log n) 分配 | 要在位图里**枚举空闲段**，O(位图)；必须自己加索引（§5）|
| 每次分配几十 ns 的元数据开销 | 持久路径上一次分配可能重写一整块 4 KiB 并重算 CRC；纯 RAM 下退化成"翻一个 bit + 条目读改写" |
| 每页有主（反向映射 page → owner）| 格式里**没有**；只能靠 §4 的内存表 |
| 引用计数 / 共享 / COW | 计数与共享位置有了（链接块 + `NLINK`）；**COW 有了，但由运行参数决定**（[`cow.md`](cow.md)）；仍缺**只读共享语义 / 快照** |
| zone / NUMA / DMA 属性 | 位图只有 1 bit；只能靠**区级属性**，粒度被迫变粗 |
| 回收 / 换出 / 迁移 / 压缩 | 都没有（[`proscons.md`](proscons.md) C8：无在线 defrag）|
| 中断上下文里能分配 | 不行：要读/写块、算 CRC、可能改目录链 |
| 多核并发 | **单写者**：格式里没有锁/事务（C1 的推论），只能一卷一把全局锁，做不了 per-CPU 快路径 |
| 混合粒度（huge + 小页）| v0 强制 `bit_unit == chunk`、`chunk ≤ 4096`（C8），没有多级位图 |
| 上电即可分配 | dirty 位图**必须全量重建**（P4 的代价）：时间 O(对象数 + 段数) |
| 稀疏 / 预留（`MAP_NORESERVE`）| **文件必须无缝无洞** → 无法表达"这段地址是我的、页还没填" |

**一句话**：它是"**带显式放置策略的粗粒度区域分配器**"，不是通用内存分配器。

## 8. 即使只借分配层，仍然存在的设计代价

1. **跨块条目删除的崩溃窗口**（[`2-dir.md`](2-dir.md) / [`proscons.md`](proscons.md) C3）：
   写序是"先清尾部块、最后删 NAME"，崩在中间留下"被截短的文件 + 泄漏"（一致、不别名，但那次崩溃丢数据）。
2. **碎片耦合 + 无 defrag**：两级碎片叠加，大块 / 对齐请求可能失败。
3. **命名空间成了负担**：区有名字、有父目录、有改名语义，而内核内存管理不需要这些；
   用起来大概是"给每个区起个编号名"，等于把目录层架空。
4. **持久性二律背反**：
   * 易失 RAM → 持久化优点（P4 / P9）完全用不上；
   * 持久内存（NVDIMM / 电池备份）→ 变成持久堆，要付重建 / 提交成本，
     而 `L` / delta 的"可平移"依然没用（物理地址搬不走）。
5. **无校验和 → 元数据损坏可能造成别名**（C5）：文件系统里"位图坏了可重建"是优点；
   内存管理里位图算错 = **同一页给两个主人**。写序纪律避免了产生路径，但位翻转只能靠 ECC 兜。
   共享（硬链接）让这类错误**更难被发现**：两个名字指向同一块在语义上本来就正常。
6. **错误语义要翻译一层**：`ENOSPC` / `EIO` / `ESTALE` / `EFRAG` → `OOM` / 不可用；
   而且"泄漏可回收"这套兜底在内核里**没有可用时机**去扫全树。
7. **诊断成本**：现场（panic / 转储）里要"谁占着这个地址"的即时答案 → 反查表必须一直维护，
   于是又多一份必须与位图保持一致的状态。

## 9. 真要做，缺的设计件（按重要性）

1. **反向映射**（page / chunk → owner）：没有它就无法回收、无法 COW、无法诊断。
2. **zone / 属性**：现在只能靠区级属性（粒度粗）。要细就得改位图语义（一 bit 变多 bit）。
3. **compaction / migration**：物理连续性（页表、DMA、huge page）比磁盘更吃紧。
4. **中断安全路径 + RAM 里的空闲段索引 / 游标**：否则热路径不可用。
5. **可选的持久提交**（日志 / shadow 位图）：只有走持久内存路线才需要，否则每次上电全树扫描。

已经不是问题的两条（本轮格式改动顺带解决）：

* **共享**链接块**：`block_type=3`（`NLINK` + 位置）就是"没有 inode 表的按需 inode"；
* **元数据溢出**：目录链续段 + `PADn`，段表长度没有格式上限（写侧待实现）。

## 10. 两条真正站得住的用法 + 一条备选

### (A) 只借"分配层"（最省、最实用）

把 [`1-alloc.md`](1-alloc.md) 那套（位图 + 区域描述符 + 策略）单独拿去当**粗粒度物理区分配器**：
DMA 池、huge page 池、固件保留区的账本。**数据面完全交给 MMU**，EasyFS 只在控制面出现
→ 它的慢路径根本不在热路径上。

### (B) 命名内存区对象管理器（收益最大、工作量最大）

微内核式的 memory object 服务：`mmap` 一个区 = 建一个"文件"，把段表交给 MMU，之后读写不经过 EasyFS。
此时**命名 + 层次 + 持久 + 两端伸缩 + 硬链接计数**全都是优点；要补的是反向映射与 COW（§9）。

### (C) 持久堆 / RAM disk / 崩溃转储区

格式完全可行（16 GiB 无压力），但**必须是 C 实现**（Python 参考实现连 16 GB 的
`bytearray` 都建不出来）；启动时"dirty → 全量重建位图"的代价要算进去。

## 11. 两条容易搞反的结论

1. **P2（双向伸缩）在内存场景里有用**：固件在低端吃掉一块内存 / ACPI 报出保留区，
   对应的是**左缩 / 左扩** —— 一次块写就改完，而"存绝对地址"的设计做不到。
2. **P1（卷内无绝对地址）价值下降**：物理地址本来就是绝对的，RAM 搬不走；
   它只剩下"池子的窗口可以在地址空间里左右挪"这一层用处，而那正是 P1 的能力。
   真正有用的是 **P2 和 P4**，不是 P1。

## 12. 参考：一个内存分配器本来会用什么

| 场景 | 常规做法 | EasyFS 的位置 |
|---|---|---|
| 物理页框 | 位图 + buddy（free list 分级）| **位图语义相同**，缺分级 free list 与反向映射 |
| 小对象堆 | slab / magazine / per-CPU cache | 完全在"区内小分配器"那一层，EasyFS 不参与 |
| 大块 / DMA | 预留池 + 对齐约束 | 需要一个 `align` 参数 + 区属性（§3）|
| 共享内存 | 引用计数 + COW + 反向映射 | 计数有了（`NLINK`），其余没有 |

**结论**：EasyFS 可以当"**内存账本 + 区域放置策略引擎**"，不要当"内存分配器"本体。
