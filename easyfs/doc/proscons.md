# EasyFS 的 pros / cons

> 把 EasyFS 和别的文件系统放在一起比：**该夸的夸、该认的认**。
> 对比对象：`ext4` / `XFS` / `Btrfs` / `ZFS`（Linux 主流）、`FAT32` / `exFAT` / `NTFS`
> （可移动介质与 Windows）、`littlefs` / `SPIFFS` / `YAFFS` / `JFFS2`（嵌入式）。
>
> **本文只谈"格式 / 设计"层面的好坏** —— 即"换一份实现也依然成立"的性质。
> 参考实现用什么语言、跑多快、工具链现状（fsck / FUSE / 内核驱动 / C 实现）、工程进度，
> 这些**实现层**的东西不在本文范围内，见各自的模块文档与工具文档。
>
> 规格见 [`common.md`](common.md)、[`layout.md`](layout.md)、[`1-alloc.md`](1-alloc.md)、
> [`2-dir.md`](2-dir.md)、[`4-file.md`](4-file.md)。

## Pros：改进 / 与别人不同的地方

### P1 卷内不含绝对地址（这条最独特）

卷内只有两种坐标：**自相对 delta**（基准是"存放这个指针的那个块"，见 [`common.md`](common.md)）
和**卷内逻辑坐标 `L`**（[`layout.md`](layout.md)）。

| 结果 | 说明 |
|---|---|
| **整卷平移零元数据改写** | 把 `[start, start+region_len)` 整体挪到别处，所有内部指针自动跟着走。ext4/XFS/Btrfs/NTFS 的块号是绝对的（ext4 的 `bg_block_bitmap`、NTFS 的 `$MFT` 记录号），换起点就得全盘搬迁元数据 |
| **左扩可以便宜** | `data_lo_logical -= N` 就完了，老数据的 `L` 一个都不变；已有多数文件系统**只在右侧能扩** |
| 目标可寻址 | `L` 是 `i64`，所以左扩以后新空间自然拿到负数编号，不需要"压缩重编号" |

代价：指针是相对的，**不能把块单独搬到别处**（没有全局唯一的块标识），
所以做不了"按块去重的快照 / 克隆"（ZFS/Btrfs 的看家本领）——
这也是"外部工具认不出这个卷"的根源（见 C7）。

### P2 双向伸缩便宜且不需要 compaction（P1 的直接红利）

| | 右扩 | 左扩 | 右缩 | 左缩 |
|---|---|---|---|---|
| EasyFS | 搬 anchor + 链尾加位图块 | 搬 anchor + 链头加位图块，`data_lo_logical -= N` | 边界空闲即删链尾块 | 同左 |
| ext4 | 可以（`resize2fs`，先扩分区） | **不行**（块号绝对） | 可以（离线，要搬块组） | 不行 |
| XFS | 可以 | 不行 | **不行** | 不行 |
| Btrfs/ZFS | 可以 | 不行（要整体搬迁） | 可以 | 不行 |
| FAT/exFAT/NTFS | 可以 | 不行 | 受限 | 不行 |

关键在于**位图块是"自描述区域"**（[`1-alloc.md`](1-alloc.md)）：每块记住自己管
`[region_off, +region_bytes)` 和这个区域的 `L` 起点，块之间是双向链表、**按位置有序**。
所以增删只在链的两端发生，**没有"块组号"要重编号**，一次 1 TiB 左扩的代价是
**1 次 64 KiB 块的写入**（[`1-alloc.md`](1-alloc.md)），而不是几小时的搬迁。

代价：收缩要求待缩掉的那段**能腾空** —— 位图块可以按策略挪走，
但**文件数据 / 目录块搬到边界上就直接拒绝**（`ENOTSUP`，一个字节都不改）；没有在线 defrag。

ext4 缩容虽然麻烦，但它**能**搬块组；我们不行。

### P3 迁移 / 复制方便（P2 的直接红利）

**整卷字节原样复制到别处就能用 —— 连头指针都不用改。**

卷内引用只有两类：**自相对 delta**（两端一起搬 ⇒ 值不变）与**逻辑坐标 `L`**
（基准 `data_lo_logical` **随卷一起搬** ⇒ 值不变）；anchor 靠"区域首尾"的位置约定找到，
不是被指到的。于是"搬位置"退化成一次 `memcpy`：

```
实测：8 MiB 卷从偏移 0 逐字节复制到另一个文件的偏移 3 MiB
      → 直接挂载 ✓ 读写 ✓ fsck 12 项全过 ✓（uuid 保留或换新都行）
```

对比：ext4 / XFS / NTFS 把**绝对块号**写进 inode / extent / 位图 ⇒ 搬家要重写所有指针
（实际做法几乎都是"整盘镜像 + 改分区表"）；Btrfs / ZFS 也有 vdev 标签里的绝对位置概念。

**边界（说清楚，别当成万能）**：

| 情形 | 结论 |
|---|---|
| **同尺寸**搬位置 | **纯复制、零改写** ✓（工具 `tool migrate`）|
| **改尺寸** | 退化成"复制 + 伸缩" —— `region_len`、位图区域平铺（I7′，见 [`1-alloc.md`](1-alloc.md) 的混合粒度一节）、`peer_delta` 都烘了尺寸（[`1-alloc.md`](1-alloc.md)）|
| 容器层（MBR/GPT 分区表、VHD 页脚）| **不是自包含的** ✗ 目标要重写 |
| 池成员（将来）| 搬位置要**保留**成员 GUID ✓；"克隆成员"会产生 GUID 冲突 ✗ → 只允许移动 |
| uuid | **移动** ⇒ 保留 ✓；**拷贝** ⇒ 建议换新 ✓（`--keep-uuid` 可保留）|

### P4 空闲位图是纯派生数据

`I3`（[`common.md`](common.md)）：位图 = "从根可达集合"的补集，**可以整个重建**；
位图块自身的布局（区域链、anchor 指针）才是权威元数据，而且它们也都能从 anchor 重新推出来。

| 结果 | 别家怎么做 |
|---|---|
| 位图可以脏、可以过期、可以丢，靠一个 `dirty` 标志 + 挂载时重建兜底 | ext4 的空闲元数据（块位图 + 空闲 inode 位图）是**权威数据**，损坏就得 `fsck -f` 重建，且重建期间必须离线 |
| 掉电后最坏是"多算了一点已用空间"，不会把别人的数据当空闲 | 位图损坏在 ext4/XFS 上可能导致**双重分配**（互相覆盖数据） |
| 写入顺序里位图在"数据 → 位图 → 目录"中间，崩了就靠重建（[`1-alloc.md`](1-alloc.md)） | 需要日志/COW 才能保证 |

代价（这一条换来的另一个代价是 C6）：

* **位图不带载荷 CRC**（只有通用头 CRC），一个位翻转可能被"重建"掩盖过去，
  也可能让重建结果和实际的引用不一致 —— 只能靠离线检查发现（[`1-alloc.md`](1-alloc.md)）。
* 正因为位图是"可以整块重算的派生数据"，它才**没有做成带索引的严肃分配器**（见 C6）。

### P5 没有 inode：文件就是它的目录条目

映射（哪些段是文件内容）**内联在目录条目的 TLV 属性里**（[`4-file.md`](4-file.md)）：
`DATA_TINY`（≤255 B 直接内联）+ 若干 `DATA_PTR`（14 字节/段）。

| 结果 | 别家怎么做 |
|---|---|
| **小文件零分配、一次写入即可见**（≤255 B 就一条 4 KiB 目录块写，带 CRC） | ext4 有 `inline_data`、NTFS 有 resident data，但都要额外开关/结构；FAT/exFAT 必须占簇；ext2/3 必须占 inode + 数据块 |
| **改名/移动只动目录条目**，数据与映射一个字节不改，不需要更新 inode 表 | ext4 改名要更新两个目录项 + inode 的 `i_ctime`（元数据多、要日志） |
| 没有 inode 表 → 没有"inode 用光了但空间还有"的经典问题 | ext4 会出现 `ENOSPC`（inode 耗尽）；NTFS 有 `$MFT` 预留 |
| 文件大小是**派生值**（内联长度和段长之和），不存 `size` 字段 | 少一个可能不一致的字段，但也意味着"改大小"必须改条目 |
| 没有 inode | 单名文件**零分配**；硬链接按需升格成对象块（[`3-object.md`](3-object.md)）—— "没有 inode"只对**内联/直接指向**的文件成立：**对象形态**的文件可变部分住在对象里，等于让出这条的一半（[`cow.md`](cow.md)）。好处是**没有"inode 用光"问题** |

顺序写的大文件通常只有 **1 条 `DATA_PTR`**（因为分配器每次要"当前最大的连续空闲段"，
[`1-alloc.md`](1-alloc.md)），所以目录条目**不随文件大小增长，只随碎片度增长**。

### P6 元数据块大小可变（位图"大块"）

位图块的 `block_bytes` 是**每块自己声明**的，可以从 4 KiB 一直到 1 MiB−1，
`mkfs` 按卷大小自动选型（从 4 KiB 起翻倍，直到块数 ≤ 1024，[`1-alloc.md`](1-alloc.md)）。效果：

| 卷大小 | 块大小 | 位图块数 |
|---|---|---|
| 256 MiB | 4 KiB | 3 |
| 16 GiB | 4 KiB | 132 |
| 1 TiB | 64 KiB | 513 |
| 16 TB | 1 MiB | 513 |

所以 16 TB 卷的位图链只有 513 个块（而不是 13.4 万个 4 KiB 块）。
ext4 的块组位图是固定小块、数量 ∝ 卷大小；这个设计是"分配单位可以远小于元数据块"的产物。

代价：单块越大，**一次改动要写的字节越多**（1 MiB 块上翻一个 bit 也要写整块），
对 NOR 磨损不友好 —— 这也是 [`1-alloc.md`](1-alloc.md) 第 6 条要讨论环形槽位的原因。

### P7 数据块零开销

数据块是**裸的 4 KiB**：没有块头、没有校验、没有链指针、没有 tag。
对比：FAT 每簇要在 FAT 表里占一项；ext2/3 要靠间接块；YAFFS/JFFS2 每个 chunk 都要带 tag/节点头；
littlefs 的数据在 CTZ 链里还要跳着找。

| 结果 | 说明 |
|---|---|
| 空间利用率高 | 一个 4 KiB 文件占 4096 字节，不是 4096 + 元数据 |
| **段内覆盖是纯数据写** | 这是 [P8](#p8-范围读--范围写都便宜尤其覆盖写) 能这么便宜的直接原因。⚠️ 只对**内联/直接指向**的文件成立；**按 `--cow` 运行时**，对象形态的覆盖写退化为"读旧→复制到新块→重映射"（[`cow.md`](cow.md)）|
| 代价：**没有块级自描述**（不能单独扫盘重建目录，随机读要靠段表） | 对比：ext4 的 inode 表可以整体扫描来恢复目录 |
| 代价：**安静的数据损坏无人发现** | 见 [C5](#c5-没有数据校验和没有坏块冗余) |

### P8 范围读 / 范围写都便宜（尤其覆盖写）

| 操作 | 代价 |
|---|---|
| 范围**读** | 段是顺序的，跳过不相交的段，只读相交的字节（[`4-file.md`](4-file.md)） |
| 范围**写（段内覆盖）** | **零元数据写**（调用方不要求更新时间戳时），不碰位图、不碰映射、不分配 |
| 范围**写（越过 EOF）** | 按追加：位图 + 目录块 |
| 写**空洞** | 不支持（`ENOTSUP`）—— 文件必须无缝 |

ext4/XFS/NTFS 的覆盖写也都便宜（本来就直接改块），所以这一条不是"比别人强"，
而是"我们**也**没在裸数据块上白白加一层"——很多简单 FS（YAFFS/JFFS2/SPIFFS）
因为每个 chunk 带 tag/索引，覆盖写反而要额外处理。**我们的优势是"不用额外做什么"。**

### P9 提交点是"一次 4 KiB 块写"，不需要日志

> 这条在**文件级**也成立：**按 `--cow` 运行时**，用**对象根块的一次写**作为提交点（[`cow.md`](cow.md)），
> 所以"不覆盖 + 原子提交"**不需要日志**（C1 继续成立）。

目录块的修改是**块内 memmove** 或 **`PADn` 等长覆盖**（[`2-dir.md`](2-dir.md)），没有空闲链表、不需要全局 defrag，
所以一次 4 KiB 写（带载荷 CRC）就是一次逻辑提交；配合写顺序纪律
（[`1-alloc.md`](1-alloc.md)），崩溃只会留下"泄漏"（可回收）、
不会留下"双重分配"（互相覆盖）。

- ext4 需要 journal（`data=ordered` 时还要保证数据先落地）；
- NTFS 有 `$LogFile`；
- FAT/exFAT **完全没有**保护，掉电遇到 FAT 表更新会留下交叉链接的簇；
- littlefs 用元数据对 + COW 做到原子，但代价是每次改动写两份元数据块。

代价：**没有多块原子事务**。比如"跨目录移动"崩在中间会短暂出现两份同名条目
（[`2-dir.md`](2-dir.md)），需要离线检查消解；ext4 的 `rename()` 是原子的（见 [C1](#c1-没有日志没有事务)）。

### P10 格式复杂度极低（没有 B 树 / 日志；COW 只按需）

格式只有：定长小端结构 + 按偏移读写 + CRC-32。没有 B 树（XFS/Btrfs/NTFS 有）、
没有日志（ext4/NTFS）、没有需要动态分配的结构（目录块链按需增长）。
**COW 只按需**：是否 COW 由**运行参数**决定、格式里不记录（[`cow.md`](cow.md)），
②③ 形态仍是"原地改 + 单块提交点" —— ZFS/Btrfs 那种"全格式强制 COW"我们没有。
**任何实现都可以做得很小** —— 包括没有 `malloc`、没有 libc 的裸机；
**也不需要"先格式化出一大批固定元数据"**（没有 inode 表、没有块组表）。

同量级的对手是 littlefs / SPIFFS，它们的核心机制是"元数据对 + COW"或"页内对象索引"，
**没有位图、没有双向伸缩、没有逻辑坐标**；littlefs 还多了格式内置的磨损均衡与更强的
掉电原子性 —— 那是我们**没有**的（见 [C1](#c1-没有日志没有事务) 与附 B）。

## Cons：缺点 / 明确不如别人的地方

### C1 没有日志、没有事务

掉电时：

- 位图可能脏 → **挂载时全量重建**（[`1-alloc.md`](1-alloc.md)）。卷越大重建越慢（见 C6）。
- 目录修改可能丢最近几条（位图/提交模式决定丢多少，[`1-alloc.md`](1-alloc.md)）。
- 跨块操作不原子：跨目录移动可能留下两份同名条目；写中途失败可能留下已分配但
  无人引用的段（泄漏，可回收）。
- 格式里没有锁、没有引用计数，所以**并发写需要外部串行化**（这是 C1 的直接推论）。

ext4/NTFS 有日志，ZFS/Btrfs 有 COW + 事务，littlefs 的元数据对是原子的。

### C2 功能面仍然很窄（链接已不再属于"没有"）

格式里**没有**：权限 / 属主 / ACL、稀疏文件、快照、克隆 / 去重、压缩、加密、配额、
扩展属性（除了自己定义的那几个）、预分配 / 延迟分配的表述、更细的时间精度（只有秒级 `u32`）。

**链接已经有了设计**（[`3-object.md`](3-object.md)）：硬链接 = 按需升格成**链接块**
（`NLINK` + 时间 + 文件位置，条目只剩 `NAME + DATA_OBJECT`）；软链接 = 三种专用属性
（`SYMLINK_TINY` / `SYMLINK_PTR` / `SYMLINK_OBJECT`，与文件四种模式 1:1）。
自带的限制：硬链接到**目录**不允许（我们的路径解析把"目录是树"当前提）、
硬链接到**软链接**不允许、软链接解析（循环 / 深度 / TOCTOU）全在调用方，
而且软链接的映射语义**有第二份实现**（[`4-file.md`](4-file.md)）。
**实现现状**：读、写都已支持（命令行要 `--object`）；**创建**（`link()` / `symlink()` / copy-on-link 升格）尚未实现。

**稀疏文件做不了**（文件必须无缝无洞，见 C8）。

### C3 大文件 + 严重碎片：写侧 v0 会失败（已不是格式限制）

格式上**条目可以顺着目录链跨块继续**（[`2-dir.md`](2-dir.md)，`CONT` 已退场），
所以段表长度**没有格式上限**。剩下的是**写侧 v0 还没实现**"尾追加 + `PADn`"策略：

```
条目装不下：这个文件被切成 384 段（数据 1.56 MiB），要 5432 字节，单块条目上限约 287 段。
格式允许条目顺着目录链跨块继续，但 v0 写入方还没实现（读侧已支持）。
卷里还有 456.00 KiB 空闲，最大连续空闲 4.00 KiB ——
要么腾出平均 ≥ 5.58 KiB 的连续段，要么先删掉一些文件。
```

对比 ext4（extent 树）/ XFS（B+ 树）/ NTFS（`$MFT` 的 runs）这些**变长、可分裂**的映射结构，
我们的方向已经一致（链式续段）；差别只在实现进度。**仍然存在的设计代价**两条：

1. **跨块条目删除要写多块**：写序是"先清尾部块、最后删 NAME"，崩在中间会留下
   "**被截短的文件 + 泄漏**"（一致、不会别名，但那次崩溃会丢一点数据）；
2. **段表很长时读取要跟着链走多块**：随机 I/O 变多（没有"跳表"式的索引）。

### C4 大目录查找是线性的

目录 = 目录块双向链，每个块内部是 TLV 流，**按名字线性扫**。
ext4 有 `htree`、XFS/NTFS 有 B 树、Btrfs 有 B 树 + 名字哈希索引。
我们虽然**预留了 `NAME_HASH`（0x41）属性**，但格式里还没有任何索引结构。

实际影响：几千项还行，几十万项的目录每次查找都要扫全链。
（小目录反而**更快**：一条 4 KiB 块里直接 memcmp，没有树的开销。）

### C5 没有数据校验和、没有坏块冗余

- 数据块**完全没有校验**（裸 4 KiB，P7 的代价），安静的数据损坏无人发现。
- 元数据有 CRC：通用块头都有，目录块**必须**开载荷 CRC；但**位图块没有**
  （它靠"重建"兜底，见 P4）。
- 格式里没有镜像 / 冗余 / 纠删码，没有 ZFS/Btrfs 那样"校验 + 自动修复"的能力。

### C6 空闲空间没有索引结构

分配要在位图里**枚举空闲段**（[`1-alloc.md`](1-alloc.md)），代价是 O(位图)，
也就是**随卷容量线性增长**；而且它只能看到"位图能表达的东西"（是否有连续空闲），
没有"按长度快速找空闲段"的索引。ext4 的 mballoc、XFS 的空闲 B+ 树就是为这个存在的。

这是 **P4 的代价**：正因为位图是"可以整块重算的派生数据"，它才没被做成带索引的严肃分配器。
要修，就得在格式里给空闲空间加一层索引（或者接受"内存里建一层缓存"这种实现层做法）。

**在 MB 级卷上这条不存在**，所以它不影响主要目标；卷越大越明显。

### C7 格式不能被外部工具理解

没有绝对地址、没有块级自描述、位图是派生的、目录是链式 TLV —— 这些都意味着
**现成工具认不出这个卷**：没有可搜的"文件签名"，`debugfs` / `testdisk` / `photorec`
这类工具都用不上，损坏时只能靠读 anchor 再自己写工具。

### C8 其他设计限制

| 限制 | 说明 |
|---|---|
| 空洞 / 稀疏文件 | 不支持（写 `offset > size` → `ENOTSUP`）—— 文件必须无缝无洞 |
| 时间戳 | `u32` **Unix 秒（UTC）**，无纳秒（到 2106 年）；时间字段只有 `TCREATE` / `TMODIFY` 两个 |
| 名字 | 最长 255 **字节**（不是字符），没有大小写规范化 / Unicode 归一化 |
| 分配粒度 | v0 强制 `chunk ≤ 4096`（保证 `data_lo` 对齐）；`bit_unit` 恒等于 `chunk`，不支持混合粒度 |
| 收缩 | 腾空阶段只挪位图块；文件数据 / 目录块占边界就拒绝（`ENOTSUP`）—— **没有在线 defrag** |
| 段表字段 | `DATA_PTR` 只有 `{偏移}{真实长度}`，分配长度靠"按 chunk 上取整"隐含推导（[`4-file.md`](4-file.md)）|

## 附 A：什么时候该用 / 不该用

**适合**

- 卷不大：**几百 KB 到几 GB**（大卷会被 C6 拖住）。
- 需要**整卷搬运**：固件里内嵌一个卷、镜像里的一段、备份直接 `cp`（P1、P3）。
- 需要**左右都能伸缩**：卷在分区里居中、两侧要留给别的系统（P2）。
- 小文件为主，元数据要极简、要能被裸眼检查（P5、P10）。
- 要一份格式同时给脚本和固件实现（P10）。

**不适合**

- 需要权限 / ACL / 符号链接 / 稀疏文件 / 快照 / 加密的通用用途（C2）。
- TB 级或对分配性能敏感（C6）。
- 需要端到端校验与自动修复（C5）。
- 不能接受"位图可以整块重建"这种兜底（C1、P4）。
- 需要在线 defrag，或者想缩到哪就缩到哪（C8）。

## 附 C：设计层短板补齐的排序

1. **写侧的尾追加 + PADn 策略** —— 让 [C3](#c3-大文件--严重碎片写侧-v0-会失败已不是格式限制) 只剩"跨块删除的崩溃窗口"那条设计代价
   （让映射从"条目内联定长段表"变成可分裂的结构）。
2. **空闲空间索引结构** —— 解决 [C6](#c6-空闲空间没有索引结构)；
   代价是位图不再那么"纯粹派生"（P4 的取舍要重新算）。
3. **目录名字哈希索引**（`NAME_HASH` 属性已经预留）—— 解决 [C4](#c4-大目录查找是线性的)。
4. **在线 defrag**（收缩时把文件数据 / 目录块也挪走）—— 去掉 [C8](#c8-其他设计限制) 里的收缩限制；
   要把跨边界的段劈开，属于"半份离线检查"的工作量。
5. **位图载荷 CRC**（或分段 CRC）—— 补 [C5](#c5-没有数据校验和没有坏块冗余) 的一个洞。
6. **段表字段显式化**（分配长度 vs 真实长度）—— 见 [`4-file.md`](4-file.md)、
   [`2-dir.md`](2-dir.md)。
