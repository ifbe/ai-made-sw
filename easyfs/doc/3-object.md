# 对象块（模块 3）

> 状态：结构已定稿。标 `[待定]` 的项见 §7。
>
> **`block_type=3` 是「对象块」**：一个位置稳定、可被多个引用者共享、带引用计数的对象。
> 两种用途共用同一个结构：

| 用途 | 谁引用它 | 相关属性 |
|---|---|---|
| **硬链接**（多名字共享同一个文件）| N 个目录条目 | `NLINK` ≥ 2 |
| **COW**（[`cow.md`](cow.md)：按运行参数选择）| 1 个条目 + 它自己作为**提交点** | `DATA_OBJECT`（**2 jump**）|

> 软链接**不属于**本文 —— 它只是"文件内容的三种编码"，已移到 [`4-file.md`](4-file.md)。
> 块头、坐标约定、不变量见 [`common.md`](common.md)；目录块与属性编码见 [`2-dir.md`](2-dir.md)；
> 文件内容的四种模式见 [`4-file.md`](4-file.md)。

---

## 1. 为什么需要对象块

没有 inode 时，**目录条目就是文件**：映射（段表）内联在条目里。硬链接要求"两个名字共享同一份
数据与同一份元数据"，而**共享需要一个位置稳定、能挂计数器的地方** —— 裸数据块（`block_type=4`）
没有块头、没有任何可挂属性的位置，所以不能当共享对象。

于是引入**对象块**：位置固定、可被任意多个条目用 `L` 指向、里面放**引用计数**和**文件位置**。

```
条目 A（目录 1）: NAME "a"  + DATA_OBJECT {L}
条目 B（目录 2）: NAME "b"  + DATA_OBJECT {L}      ← 两条目里存的 L 相同，可直接比较
                     │
                     ▼
对象块（block_type=3，链头）: NLINK {2} + TMODIFY {…} + DATA_PTR{delta,size} × n
                     │
                     ▼
              裸数据块（block_type=4，无块头）
```

**只有当真的出现硬链接时才建它**（copy-on-link，§3）：单名文件继续走条目内联，
P5"小文件零分配"的收益不受影响。

## 2. 对象块的结构

| 项 | 值 |
|---|---|
| `block_type` | **3** |
| 载荷 | TLV 属性流，和目录条目**同一套编码**（`DATA_PTR` / `DATA_TINY` / `SYMLINK_*` / `TMODIFY` …）|
| 必备属性 | `NLINK {u32}`（`0x50`）—— 引用计数（≥2；升格时写 2）。**它只出现在对象块里**，目录条目里没有 |
| 映射属性 | `DATA_PTR`（`0x31`）`{i64 delta}{u32 size}` × n，**delta 的基准是本链接块**（与条目内联时同一套规则）|
| 载荷 CRC | **必须启用**（`flags.bit0`），和目录块一样 |
| 能不能成链 | **能**：映射超过一块时按 `prev/next_delta` 续块，规则同 [`2-dir.md`](2-dir.md)（**属性不跨块** + `PADn` 补洞）；链头放 `NLINK`/`TMODIFY` |
| 归属 | 被**多个**条目共享；它自己**不含 `NAME`**（名字在指向它的条目里）|

**块内用 delta、条目→块用 `L`** 是刻意的：

* 条目层用 `L`：多个名字里**值相同**（可直接比较"是不是同一个对象"）、引用点与宿主块位置解耦；
* 块内层用 `delta`：与条目内联时**同一套编码**，解析函数只有一份。

---

## 3. 条目的链接形态与升格（copy-on-link）

**链接形态的条目**：`NAME`（`0x40`）+ `DATA_OBJECT`（`0x32`）`{i64 L}` —— **没有数据属性、没有时间属性**（§2 的 `TMODIFY`
在链接块里，两个名字共享同一份时间）。

**升格流程**（第二个名字出现时）：

```
1. 建链接块：把原条目的属性流搬进去（映射 → DATA_PTR，时间 → TMODIFY），加 NLINK = 2
2. 把原条目改写成 NAME + DATA_OBJECT{L}          （原来的数据属性/时间属性全部删掉）
3. 插入第二个条目 NAME + DATA_OBJECT{L}
```

**写序就是上面这个顺序**（新块 → 改旧条目 → 插新条目）：崩在中间最坏是
"链接块已建但没人指" = 泄漏（可回收），**原有名字始终可用** ✓ 符合"先占位后引用"。

**要不要退回内联**：不要。只剩一个名字时保持链接形态（退回要和"升格中崩溃"竞争，不值）。

---

### 3.1 命令行约定

* **硬链接必须用对象形态**（两个名字共享一份内容，①②③ 表达不了）——
  所以 `tool ctrl shell` 里 **`ln` 默认拒绝**，要显式给 `--object`；
* 软链接**不走对象**：`SYMLINK_TINY` → `SYMLINK_PTR` 就够（`SYMLINK_OBJECT` 是 `[待定]`）；
* 目录**默认永远是链式**（`DIR_PTR`）：`DIR_OBJECT` 只有将来做目录级 COW 时才用。

---

## 4. 删除与计数

```
删一个名字：删条目（先解引用） → NLINK--  →  归零才释放数据段 + 链接块本身
```

* 顺序不能反：先减计数可能提前释放 → 另一个名字变悬挂引用；先解引用只会让计数偏大（泄漏）。
* **目录不允许硬链接**（照 POSIX 防环）。我们的路径解析把"目录是树"当前提
  （`PathWalker` 只在内存维护路径链、卷里没有 `..`），多父引用会让路径不唯一、还可能成环。
* **不允许硬链接到软链接**（§5）：创建时返回 `ENOTSUP`；fsck 检查"`DATA_OBJECT` 指向的对象不得带 `SYMLINK_*`"。

## 5. fsck 检查清单（对象层）

1. `DATA_OBJECT` 的 `L` 能换算成合法物理地址，且那一块确实是 `block_type=3`。
2. 链接块的 `NLINK` **等于**指向它的 `DATA_OBJECT` 条目数（要全树扫描才能算；不一致可修计数，
   或把无主链接块的数据挂到一个恢复目录）。
3. 链接块、它指向的数据块，在位图里都必须置位（`_walk_used` / 位图重建必须跟着 `DATA_OBJECT` 走）。
4. 链接块里**不允许**再出现 `DATA_OBJECT`（不嵌套）。
5. `DATA_OBJECT` 指向的对象**不得**带 `SYMLINK_*`（硬链接到软链接 = 不允许）。
6. 链接形态的条目**不得**同时带数据属性或时间属性（它们归链接块）。
7. 软链接相关检查见 [`4-file.md`](4-file.md)。
8. 链接块的 `header_crc32` 与**载荷 CRC**（必须启用）。

## 6. 结构可插拔：三层都用同一套思路（设计方向）

对象层 = **一个稳定的根 + 一张映射表** ✓。**表本身的数据结构不做死**：默认最简单，按需要逐级升级
（这正是 ext4 `inline extent → extent tree`、XFS `di_format: EXTENTS → BTREE`、ZFS `BP 树`、
NTFS `常驻 → 非常驻 + attribute list` 走过的老路 ✓）。

| 级 | 结构 | 什么时候升上来 | 状态 |
|---|---|---|---|
| 0 | **没有对象**：条目内联（`DATA_TINY`）或直接 `DATA_PTR × n` | 小文件 | ✓ 已有（[`4-file.md`](4-file.md) 的 ②③）|
| 1 | **单块数组**：对象块载荷 = `DATA_PTR × n`（≤ 288 段）| 条目装不下 / 要硬链接共享 | ✓ 已有（本文件 §2）|
| 2 | **链式多块数组**：对象块用 `prev/next_delta` 串起来 | 段数超过一块 | ✓ 已有（§2）|
| 3 | **A/B 双槽**：同一块里切两半，作**原子换根**的提交点 | 要 COW（[`cow.md`](cow.md)）| ✗ 未实现 |
| 4 | **索引块 / B 树**：随机读写大文件、段数极多 | 大文件 / 频繁改映射 | ✗ 未实现 |
| 5 | **extent + 计数**：映射项从"块"变成"extent + 引用计数" | reflink / 快照 / 去重 | ✗ 未实现 |

**三条硬要求**（先定下来；以后每加一种结构都按它走，免得每加一次都要改读路径和 fsck ✗）：

1. **根必须稳定、且能原子替换** ✓ —— 条目只认"对象块"这一个入口 ✓；升级 = 写新结构 + **一次换根** ✓；
   崩在中途 ⇒ 旧结构仍然完整 ✓（这就是第 3 级 A/B 双槽的意义 ✓）。
2. **结构必须自描述** ✓ —— 对象块载荷本来就是**属性流（TLV）** ✓ ⇒ **用"出现哪个属性"当结构标记** ✓
   （有 `DATA_PTR` = 数组 ✓；将来有 `BTREE_ROOT` = B 树 ✓）；**第一个属性必须是"布局"属性**
   （像目录条目里 `NAME` 必须第一个 ✓），读方按它分派；**不认识的布局 ⇒ 拒绝并报告**（可诊断优于猜 ✗）。
3. **必须有统一的"枚举"接口给 fsck / 遍历** ✓ —— 不管哪种结构，都要能回答"**这个对象引用了哪些块**" ✓
   （可达遍历、`df`、scrub 全靠它 ✓）。**加结构 = 加一个枚举实现，不改调用方** ✓。

**降级**：升级容易，降级也要有路 ✓ —— 交给 `optimize object`（见 [`1-alloc.md`](1-alloc.md) 的 `optimize` 命令一节 ✓）：把 B 树压回单块数组、把链合成一块 ✓（ext4/XFS 都不降级 ✗，而我们正好有显式的
`optimize` 命令 ✓）。

### 6.1 目录层：`DIR_OBJECT`（同一套思路）

目录默认是**链**（`DIR_PTR` → dir 块用 `prev/next_delta` 串起来 ✓）；要 COW 时升格成**对象形态**
（`DIR_OBJECT` → 对象块，载荷 = **目录的内容块表** ✓；读侧已实现 ✓）。

**"链"为什么不能拿来做 COW**（这是目录 COW 的病根 ✓）：

| 结构 | 改目录里**一个**块要动谁 | 对 COW |
|---|---|---|
| **链**（现状）| 块 A ⇄ **B** ⇄ C：写 B′ 之后 **A 的 `next`、C 的 `prev` 都得改** ✗，而 A、C 也是目录块 ⇒ 继续扩散 ✗ | ✗ 邻居耦合 ⇒ 就是所谓"粒度放大" |
| **对象形态（块表）** | 表 = `[B1, B2, …]`，各块**互不引用** ✓ ⇒ 写 B2′ + 改表里第 2 项 ✓ | ✓ 只动"新块 + 一个表块" |

再加一条关键性质 ✓：**父目录不用改** —— 父条目里存的是 `DIR_OBJECT`（稳定引用 ✓），表怎么变它都不变 ✓
⇒ **改动沿目录树的传播，在"每一级自己的对象"处终止** ✓（这正是"一次换根"能成立的全部原因 ✓）。

**目录 COW 还差三件配套**（缺一不可 ✓）：

1. **`DIR_OBJECT` 的写侧** ✗（现在**只有读侧** ✓）；
2. **"dir 块只写新块"的写入方约定** ✓（和文件一样：活数据永不原地覆盖 ✓）；对象形态下
   **dir 块之间不再有链** ✓（**表是唯一顺序来源** ✓ —— 读侧已经这么走 ✓）；
3. **旧块回收** ✓：旧 dir 块 / 旧表节点靠**引用计数或延迟释放** ✓ —— 正好用上通用头里新定的
   `refcount` / `owner_gen`（见 [`common.md`](common.md) 的通用头那一表 ✓）。

**表长成树**（大目录 / 要 O(log n) 找名时才需要 ✓）：

| 表的结构 | 查找 | COW 一次改动的代价 |
|---|---|---|
| **单块数组**（≤288 项 ⇒ 约 1.1 MiB 目录内容 ✓）| O(n) | ✓ 一次换根 —— **默认够用** |
| **链式多块数组** | O(n) | ✗ 又把"邻居耦合"带回来了 ⇒ **别拿它做 COW** |
| **树（B 树 / 哈希索引）** | O(log n) | ✓ 路径复制：O(log n) 个新节点 + 一次换根 |

树必须**父持子指针** ✓（不能像链那样双向互指 ✗）；键就用早就预留的 **`NAME_HASH`（`0x41`）** ✓
⇒ 做成 ZFS ZAP / btrfs dir-index 那种"按名索引"的树 ✓。

### 6.2 分配器层：`bitmap_OBJECT`（同一套思路，但**目的不同**）

分配信息默认也是**扁平位图链** ✓（anchor 里的 `allotype` / `alloioff`（默认 `1` = 扁平链） ✓）；同样可以升格成**对象**
（`bitmap_OBJECT`：anchor 的指针指向一个对象块 ✓，载荷是属性流 ✓，由它自己再套索引 / 多层 ✓）。

**但这里和文件 / 目录有个本质区别** ✓：

| 对象 | COW 之后得到什么 |
|---|---|
| 文件 / 目录 | ✓ **旧版本还在**（旧块被旧版本共享 ✓）—— 内容只在被改动处变化 ✓ |
| **分配器** | ✗ **"换一份新版位图"等于什么都没得到** ✗ —— 有快照时，**"空闲"本身就是按世代的**：同一块对旧世代是"还被引用"、对新世代才是"空闲" ⇒ **一张扁平位图无法表达** ✗ |

⇒ 所以 `bitmap_OBJECT` 里装的**不能只是"更多层位图"** ✗，必须是**可版本化的分配记录** ✓，只有两条路：

| 路线 | 做法 | 谁在用 | 代价 |
|---|---|---|---|
| **A. 按世代增量** | 记"在 `gen ≥ N` 时，这些块被释放了" ⇒ 分配器 = **变更记录的树** ✓ | ZFS 的 spacemap（按 txg）✓ | 结构随时间增长 ⇒ 需要 compaction |
| **B. 引用计数** | 分配信息 = **`refcount > 0`** ✓，归零才算空闲 ✓ | btrfs / XFS（rmap + refcount）✓ | 每次写都要改计数 ⇒ 写放大；但结构有界 ✓ |
| C. 挂载时重建（现状 ✓）| 位图就是**派生缓存** ✓ | 单世代卷 ✓ | **O(data) 重建** ⇒ 大卷 + 快照不可接受 ✗ |

**两个必须一起定的问题** ✓：

1. **自举**：分配器**自己也占块** ✓ ⇒ 它的块从哪来？别人的规矩：APFS 的 internal pool（预留池）✓、
   btrfs 的 metadata reservation ✓、ZFS 的 spacemap **自寄生于自己的 metaslab** ✓ —— 我们要**明确选一条** ✓。
2. **写放大**：分配器**几乎每次写都会变** ✗ ⇒ 一旦 COW / 树化，每次提交就多一条"到分配器根"的
   路径拷贝 ✗。缓解办法照抄 ZFS：**追加式的 spacemap 块 + 内存里聚合**（块写满才换新块 ✓）。

**阶梯**（与前两层同构 ✓）：

| 级 | 分配器形态 | 何时升上来 |
|---|---|---|
| 0 | **扁平位图链**（现状 ✓）+ 挂载 / 拷问时重建 ✓ | 单世代卷 ✓ |
| 1 | 扁平位图 + **按 `gen` 的延迟释放队列** + 多世代根 ✓ | 刚上快照 ✓（最小闭环）|
| 2 | **`bitmap_OBJECT`**：按世代增量（路线 A）或引用计数（路线 B）✓ | 大卷 / 不想"每次都靠重建" ✓ |

**任何时候都保留** ✓：`fsck` / `optimize` 能**从引用结构重建位图** ✓ —— 这是"位图永远是派生数据"
这条安全网 ✓，也是它和文件 / 目录最不一样的地方 ✓。

> 顺带：「跳数」那张表（[`4-file.md`](4-file.md)）现在是按"目录 → 对象 → 数据"数的 ✓；
> 结构升级后**跳数由结构决定**（B 树会多几跳 ✓）⇒ 那一列要理解成"**最少跳数**" ✓。

## 7. 上限与待定项

> **实现现状**：硬链接（`link` / `unlink`，含 `NLINK` 递减与归零释放）与软链接
> （`symlink` / `readlink`，短目标 `SYMLINK_TINY`、长目标 `SYMLINK_PTR`）**都已实现** ✓；
> 命令行侧 `ln` 走对象形态，需要显式 `--object`（见 §3.1）。
> **`DIR_OBJECT`（目录的对象形态）只有读侧** ✓，写侧未实现。


| 项 | 值 |
|---|---|
| 一个链接块的映射 | 与条目一样受"单块 ≤ 4032 B"约束；超过就**成链**（§2）|
| `NLINK` | `u32`；到 0 就释放（不会有"计数回绕"问题，因为 0 即销毁）|
| 软链接目标 | `SYMLINK_TINY` ≤255 B；更长用 `SYMLINK_PTR` / `SYMLINK_OBJECT`（大小不受 255 限制）|
| 名字 | 仍是 ≤255 **字节**（[`2-dir.md`](2-dir.md)）|


   **创建**（`link()` / `symlink()` 与 copy-on-link 升格）**已实现**（命令行要 `--object`），调用会返回 `ENOTSUP`。
2. **[待定] 对象块的压实**：与目录块一样靠 `PADn` + 写时局部整理（[`2-dir.md`](2-dir.md)）。
