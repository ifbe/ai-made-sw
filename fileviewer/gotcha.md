# gotcha

开发过程中踩到或查出来的坑。每条都尽量写清**现象 → 原因 → 怎么处理**，
以及是**实测确认**还是**推断**。

---

## 一、KiCad 文件格式

### 1. 封装旋转的矩阵写错了会变成"反射"

**现象**：旋转过的封装，焊盘位置整体跑偏。CM5IO 上有 26~32 个焊盘落在板框外，
最远超出 **39.89mm**（一个 GPIO 排针整个飘在板子外面）。

**原因**：原式是

```js
px = lx*cos - ly*sin
py = -lx*sin + ly*cos      // ← 注意这里是 -lx*sin
```

对应的矩阵是 `[[cos, -sin], [-sin, cos]]`，**行列式 = cos2θ**，根本不是旋转矩阵：

- θ = 90° 时行列式 −1 → 是**镜像**
- θ = 45° 时行列式 0 → 把所有焊盘**压成一条线**

**处理**：必须是 `px = lx*cos + ly*sin, py = -lx*sin + ly*cos`（行列式恒为 1），
与渲染端 `ctx.rotate(-rot)` 的形状约定一致。修完板外焊盘 32 → **0**。

**实测确认**：CM5IO / CM4IOv5 各 32 个板外焊盘，修正后均为 0。

### 2. `gr_arc` 不解析 → 板框永远闭不上

**现象**：板框在 3D 里出不来，退化成包围盒；板子尺寸算出来是 `199.9 × 90.0`，
而真实尺寸是 **160 × 90**。

**原因**：KiCad 的板框圆角基本都是 `gr_arc`。CM5IO 的板框是 **4 条直线 + 4 段圆弧**，
不解析圆弧，直线段之间就是断开的，串不成闭合环。

**处理**：解析 `gr_arc` 的 `start`/`mid`/`end` 三点 → 求外接圆 → 沿正确方向采样成折线，
和直线段一起参与成环。2D 渲染端也要把圆弧画出来，否则板框缺角。

**实测确认**：修完 CM5IO/CM4IOv5 板框恢复为 160×90mm，1 个闭合环、80 个顶点。

---

### 3. `gr_arc` 采样不能只看起止点定方向

**现象**：圆弧采样"绕远路"，几何被撑大（某个测试点模型包围盒从 2.5mm 变成 8.6mm）。

**原因**：圆弧的行进方向**不由起止点决定**，而由两个布尔量共同决定：

- `ORIENTED_EDGE` 的 `orientation` —— 这条边相对 `EDGE_CURVE` 的 v1→v2 是否正向
- `EDGE_CURVE` 的 `same_sense` —— v1→v2 是否等于曲线参数增大的方向

两者**相同则沿参数增大方向，不同则反向**（异或）。忽略 `same_sense` 就会绕远路。

**处理**：`ccw = (orient === sameSense)`。

---

### 4. `(model ...)` 里的欧拉角要取负

**现象**：带旋转的元件模型摆放位置不对。

**判据**：模型在**封装局部坐标系**里的 XY 范围必须盖住该封装焊盘的局部范围。

| 约定 | 带旋转模型的正确数 |
|---|---|
| 角度原样代入 `Rz·Ry·Rx` | 1 / 6 |
| **角度取负** | **4 / 6** |

**原因**：取负等价于旋转矩阵转置，即 KiCad 用的是 `R⁻¹` ——
与它把模型变换写成"世界→模型"是一致的。

**处理**：`eulerXYZ(-rx, -ry, -rz)`。

**注意**：这条是**推断 + 实测拟合**，不是从 KiCad 源码确认的。详见第 5 条。

### 5. 两处厂商 offset 放不到板上（未解决）

**实测确认的异常**：

| 位号 | offset | 现象 |
|---|---|---|
| J5 / J16（FH12 FFC 座） | `(16.5, -10.6, -128)` | 落在板下 128mm |
| J7 | `(-135.9, -16.4, 154.4)` | 落在板外 `(337, -169, 154)` |

**排查过的**：

- 试了 **24 种**变换约定（6 种欧拉序 × 角度取负与否 × 转置与否）—— 无一能让它们落到板上
- 确认模型文件本身**没有远处几何**：`VERTEX_POINT` 包围盒与渲染网格完全一致
  （FH12 就是 2.1 × 6.4 × 15.1mm）
- 两块**官方树莓派板子**（CM4IO 与 CM5IO）里 FH12 的 offset 几乎一样
  （`16.45,-10.6,-128` vs `16.5,-10.6,-128`），说明是同一个厂商封装带来的

**结论**：要么还有个没推出来的约定细节，要么这两个厂商封装的 3D 设置本身就是错的。
占位方块会把这件事变可见 —— 打开 3D 就能看到这几个方块飞在外面。

### 7. KiCad 引用的路径里有环境变量

```
${KICAD8_3DMODEL_DIR}/Resistor_SMD.3dshapes/R_0805_2012Metric.wrl   ← 环境变量
${KIPRJMOD}/CM5IO.3dshapes/FH12-22S-0.5SH.stp                       ← 项目目录
```

浏览器解析不了。但**实测发现根本不需要解析变量**：

形态固定是 `<库名>.3dshapes/<模型名>.<后缀>`，所以按**末两段路径**做后缀匹配就够了。

## 二、浏览器平台

### 8. 浏览器读不到任意文件系统路径

**这条决定了 UI 设计**。

`<input type="text">` 里填 `/Applications/KiCad/.../3dmodels` —— 拿到的是一个字符串，
拿去 `fetch('file:///...')` 会被 CORS 挡死（页面 origin 是 `null`）。

**所以**：

- 本地文件 → 只能靠**拖目录**或 `<input webkitdirectory>` 拿到 `File` 对象
- 文本框 → 只对 **HTTP URL 前缀**有用（`http://127.0.0.1:8000/3dmodels/` 是可以 fetch 的）

`showDirectoryPicker()`（File System Access API）能持久化授权，但 Safari/Firefox 支持不全，
所以用 `webkitdirectory` 作可移植方案。

---

### 9. `FileSystemFileEntry.file()` 会静默失败（Mac 拖拽没反应的元凶）

**现象**：Mac 上拖文件进页面**没反应**；点页面中间「选文件」却正常。

**原因**：为了支持拖目录，取文件改成了 `webkitGetAsEntry()` + `entry.file()` 的**异步回调**：

```js
fileEntries[0].file(f => loadFromFile(f), () => {});  // ← 错误回调是空的
return;                                               // ← 而且直接 return
if (dt.files && dt.files.length) loadFromFile(...);   // ← 永远到不了
```

两个错叠加：错误被吞掉 + 永远回退不到 `dt.files`。

**处理**：**普通文件一律优先用 `dataTransfer.files`**（同步、直接、可靠），
`webkitGetAsEntry` **只用来判断"是不是目录"**。

**同时补的**：

- `dragenter` 也要 `preventDefault()` —— Safari 历史上必须同时阻止 `dragenter` 和 `dragover` 才触发 `drop`
- 落点从 `mainEl` 扩到整个 `document`，避免子元素挡住
- 错误不再静默，失败要有提示

`droptest.js` 的场景 2 专门复现这个故障（`entry.file()` 永不回调），确保不回归。

### 10. `readEntries` 每次最多返回 100 条

遍历拖入的目录时必须**反复读到返回空数组为止**，调用一次是不够的。

## 三、3D 几何与算法

### 12. 带洞多边形的耳切会死锁，要靠扫描线兜底

**现象**：STEP 平面面的三角化面积不守恒，105 个文件里 **33 个**偏差，
最大 **137%**（= 大量重叠三角形）。

**排查过程**（每步都靠数据，不靠猜）：

1. 加**面积守恒自检**（参数域多边形面积 vs 三角化面积）→ 定位到问题面
2. 桥接后的多边形**面积精确等于外环减洞、零自交** → 桥接没问题
3. 卡住时**凸角存在但合法耳为零** → 不是朝向或阈值问题
4. 清理共线点/重复点 → **无效**
5. 改成严格内点测试 → **更差**（兜底 62 → 139），回退
6. 局部"最不坏耳"修补 → **更差**（偏差 120% → 229%），推翻

**根因**：洞的桥接缝是**零宽 slit**，缝两侧顶点会把所有候选耳判掉 ——
耳切在这种情况下**数学上必然死锁**。

**处理**：不再修耳切，而是**失败时切换算法**：梯形扫描线
（按 x 切竖条，用**中线**判断哪些边跨过本竖条，按 y 交点奇偶配对成梯形）。
取中线是关键 —— 竖条内部没有顶点，所以跨过中线的边一定贯穿整条，端点退化情形自然避开。

**结果**：面积不守恒 **33 → 0**。

### 13. 圆弧采样要按弦高容差，不能固定段数

固定"每整圆 48 段"对元件小圆角是巨大浪费：

| 模型 | 固定 48 段 | 弦高容差 0.02mm |
|---|---:|---:|
| LQFP-48 | 29060 三角 | **8980** |
| QFN-32 | 9096 | **1976** |
| R_0805 | 1076 | **276** |

按 `sagitta = r·(1 − cos(Δθ/2)) ≤ 0.02mm` 反推步数即可：
小半径自动降到几段，大半径自动加密。
同一个圆在任何面里半径相同，所以各面采出的点数一致，**不会产生裂缝**。

### 14. KiCad 的 VRML 模型单位是 0.1 英寸

**实测确认**：把同一模型的 `.wrl` 与 `.step` 包围盒对比，**12 个模型的比例全部精确等于 2.54**。

`.wrl` 的坐标要 **×2.54** 才是 mm。忘了这个，模型会小 2.54 倍。

### 15. KiCad 9 的库是 STEP-only，而存量板子引用 `.wrl`

| 板子 | `.wrl` 引用 | `.step`/`.stp` 引用 |
|---|---:|---:|
| CM4IOv5（KiCad 6） | **123** | 21 |
| CM5IO（KiCad 8） | **54** | 12 |

而 KiCad 9 安装目录里是 **7241 个 `.step`、0 个 `.wrl`**。
所以按原后缀找 `.wrl` 会全部落空。

**处理**：**扩展名替换**（`.wrl` ↔ `.step`/`.stp`/`.stl`）。
官方库对每个模型同名发布两种格式（本地 checkout 里 6189 对），所以替换是安全的。

**实测**：只用 STEP-only 库时，CM5IO 命中 **65/66**，其中 **54 个靠替换救回**。

---

### 16. 两套坐标系：pcbnew 的 Y 向下，3D 的 Y 向上

pcb 的 `(x, y)` 映射到世界是 `(x, −y)`。

判定变换链形式的方法：拿它和**已验证的焊盘摆放公式**对照。展开后矩阵是
`[[cosθ, sinθ],[sinθ, −cosθ]]`，**行列式为 −1** —— 说明确实是
"先翻转 Y、再绕 Z 旋转"，而不是单纯的旋转。这一条把很多歧义一次钉死。

---

### 17. STEP 里 `CARTESIAN_POINT` 不等于几何顶点

`AXIS2_PLACEMENT_3D` 的原点也是 `CARTESIAN_POINT`，可以放在任意位置。
要判断模型真实范围必须只看 **`VERTEX_POINT`**，否则会以为模型有 130mm 那么大。

---

### 18. 双面光照 + 关闭背面剔除能省掉一堆麻烦

几何在**世界空间**直接构建，法线就地算；着色器做双面光照，
`gl.disable(CULL_FACE)`。这样：

- 三角面绕序不需要严格正确
- 不需要为每个物体建 model 矩阵
- 法线也不需要逆转置（这里的线性映射是正交的：旋转 + 一次反射）

## 四、调试/测试本身的坑

### 19. `float32` 和 `double` 不能直接比

`mesh.col[i] === 0.13` 永远为 false —— 存进 `Float32Array` 后是
`0.1299999952316284`。测试里必须用容差或 `Math.fround`。

### 20. 探针里的索引写错，会得出完全相反的结论

排查第 12 条时我写过一个探针，内点测试里用了 `poly[j]` 而不是 `poly[idx[j]]`，
于是"找到 69 个合法耳"，而实际 `earClip` 一个都没有 —— **白白绕了一大圈**。
涉及"索引数组 + 顶点数组"的地方，这类错极容易犯，写探针时要格外小心。

### 21. `readFileSync(f).buffer.slice(0)` 是错的

`Buffer` 的 `.buffer` 可能是一个**共享的底层内存池**，`slice(0)` 会复制整个池。
正确写法：

```js
const raw = fs.readFileSync(f);
const ab = raw.buffer.slice(raw.byteOffset, raw.byteOffset + raw.byteLength);
```

### 22. 测试脚本自己要能发现接线错误

`app.js` 里用了 `Models3D` 却忘了声明模块引用时：

- `libtest.js` **没发现** —— 它直接加载各模块，绕过了 app.js
- **冒烟测试发现了** —— 报 `Models3D is not defined`，26 项失败

**两套测试各有盲区，都得留着。** 冒烟测试的价值就在于它走的是**真实的加载顺序和接线**。

冒烟测试现在**从 `index.html` 解析脚本清单**，所以它永远和真实加载顺序一致，
不会出现"测试通过但页面白屏"的偏差。

### 23. 桩 DOM 的事件落点要跟着代码走

拖拽处理从 `mainEl` 移到 `document` 后，冒烟测试立刻挂了 22 项 ——
因为测试还在往 `main` 上派发事件。这不是测试太脆，而是它确实盯住了接线。

### 24. 断言写反了会冤枉正确的代码

包围盒校验曾经这样写：

```js
const lo = mb.min[k] - vb.min[k];
if (lo < -0.01) → 判为"网格比顶点包围盒小"     // ← 反了
```

`lo` 为负恰恰说明**网格比顶点更靠外**（正确）。判据写反，把正确行为判成失败。

写不变量断言时，先想清楚**符号方向代表什么**。
