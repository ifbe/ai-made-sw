# CyberGear 微电机 — 参数与 CAN 协议速查

> 来源：《CyberGear 微电机使用说明书》（PDF）4.1 通信协议 / 4.2 控制模式 / 3.3.3 参数表，
> 外加本仓库在真机上的实测验证。
> 适用：小米 CyberGear 微电机 + 本仓库的 USB-CAN 串口适配器方案（`python/`）。

---

## 0. 必读：这台电机有**两套参数表**，千万别混用

| 参数表 | 地址段 | 怎么访问 | 本仓库用途 |
|---|---|---|---|
| **CAN 运行参数表**（手册 4.1.12） | `0x7005` ~ `0x7020` | CAN 通信类型 **17 读 / 18 写** | ✅ 全部控制与读取都用这张表 |
| **上位机调试参数表**（手册 3.3.3） | `0x0000` ~ `0x302f` | 厂家上位机软件（"上传/下载参数"） | ❌ **不能用 CAN 读**（见下） |

**实测反例**：用 CAN 通信类型 17 读 `0x2014`、`0x2015`（属调试表），返回的都是 `8313.374`。
两个不同地址返回同一个值 = 电机对不认识的 index 只填了 index，数据区是上一次的残留字节，**值没有意义**。

> 手册 4.1.8 里写的"参数列表详见 4.1.11"是手册串号（4.1.11 是波特率章节），实际指 **4.1.12**。

## 1. 串口帧格式（USB-CAN 适配器，AT 模式）

```
41 54 | CAN ID(4 字节, 大端, = 29位ID << 3) | DLC(1) | DATA(0~8) | 0D 0A
帧头                                            长度      数据        帧尾
```

例（读参数 0x7005，目标电机 1）：
`41 54 88 00 00 10 08 05 70 00 00 00 00 00 00 0D 0A`
→ CAN ID = `0x88000010 >> 3` = `0x11000001`

---

## 2. 29 位 CAN ID 布局

| 方向 | bit28~24 | bit23~8 | bit7~0 |
|---|---|---|---|
| **主机 → 电机**（1/3/4/6/7/17请求/18/22） | 通信类型 | bit15~8 = 主 CAN ID | 目标电机 CAN ID |
| **电机 → 主机**（0应答/2反馈/17应答/21） | 通信类型 | bit15~8 = **电机 CAN ID**<br>bit16~21 = 故障位、bit22~23 = 状态位（仅反馈帧） | **主 CAN ID** |

> ⚠ 两个方向的字段含义相反。本仓库主机 ID 固定 `0`，所以电机上报帧的低字节恒为 `0`，
> 电机 id 必须从 **bit15~8** 取。（曾经按低字节取，导致反馈帧被当"总线噪音"整帧丢弃。）

## 3. 通信类型总表

| 类型 | 名称 | 方向 | 数据区 | 应答 |
|---|---|---|---|---|
| 0 | 获取设备 ID | 主机→电机 | 空 | 电机→主机：ID 的 bit23~8 = 电机 ID，bit7~0 = `0xFE`；数据 = 64 位 MCU 唯一标识 |
| 1 | 运控模式控制指令 | 主机→电机 | 角度/角速度/Kp/Kd（力矩在 ID 里，见 §6） | 电机反馈帧（类型 2） |
| 2 | **电机反馈数据** | 电机→主机 | 角度/角速度/力矩/温度（见 §4.3） | — |
| 3 | 电机使能运行 | 主机→电机 | 空（8 字节 0） | 电机反馈帧 |
| 4 | 电机停止运行 | 主机→电机 | 正常运行清 0；**Byte0=1 清故障** | 电机反馈帧 |
| 6 | 设置机械零位（掉电丢失） | 主机→电机 | Byte0 = 1 | 电机反馈帧 |
| 7 | 设置 CAN ID（立即生效） | 主机→电机 | **新 ID 在 ID 的 bit16~23**（见 §4.4） | 设备 ID 广播帧（类型 0） |
| 17 | 单个参数读取 | 主机→电机 | Byte0~1 = index，Byte2~3 = 00，Byte4~7 = 00 | 类型 17 应答（见 §4.5） |
| 18 | 单个参数写入（**掉电丢失**） | 主机→电机 | Byte0~1 = index，Byte2~3 = 00，Byte4~7 = 值 | 电机反馈帧 |
| 21 | 故障反馈帧 | 电机→主机 | Byte0~3 = fault，Byte4~7 = warning（见 §4.6） | — |
| 22 | 波特率修改（需固件 ≥ 1.2.1.5） | 主机→电机 | Byte0：1=1Mbps / 2=500k / 3=250k / 4=125k | 设备 ID 广播帧 |

## 4. 帧格式细则

### 4.1 获取设备 ID（类型 0）—— 也是**唯一的设备发现机制**

请求：ID = `0x0000_00_xx`（bit7~0 = 目标电机 CAN_ID），数据区全 0
应答：ID 的 bit23~8 = 电机 CAN_ID，bit7~0 = `0xFE`；数据 8 字节 = MCU 唯一标识（小端）

> **手册没有"扫描所有设备"的章节**，而且全篇 `0XFE` 只出现一次 —— 就在上面**应答帧**的
> bit7~0（主机 ID 字段）；请求行写的是"目标电机 CAN_ID"，**手册从没说 `0xFE` 是广播地址**。
> 因此"总线上有哪些设备"只能靠：发通信类型 0，**谁应答谁存在**（不应答 = 不在总线上）。

**⚠ 实测结论：向 `0xFE` 发广播没有应答**（真机上试过，一帧回应都没有）。
所以本仓库**不再发广播**，改成真正逐个 id 发报文：

| 方式 | 行为 | 耗时 |
|---|---|---|
| 全扫 `scan()` / `/api/ls {}` | 依次发 GET_ID 给 **id = 1~127** 每一个（id 之间留 3ms），发完统一等 0.25s 收应答 | 约 **0.65s** |
| 定向探测 `scan(targets=[...])` / `/api/ls {targets:[7]}` | 只给这几个 id 发，适合"确认某台在不在" | 每 id 约 0.25s |

- id 范围依据：手册调试表里 `CAN_ID` 最大 **127**，而主机 id 是 0，所以电机 id 只能是 1~127。
- 扫描期间会**占着串口锁**（约 0.65s），这期间 `stop`/`enable` 等要排队；这是手动操作，可接受。

⚠ **用扫描结果判断"存在"有个坑**：`get_motors()` 返回的是**累积缓存**，
曾经应答过的电机即使后来断电，仍然留在列表里。所以"本次是否真的在总线上"必须看
应答有没有刷新 `last_update`（GET_ID 应答会刷新它）：

- `/api/ls` 的返回消息现在会写：`扫描完成: 本次应答 2 台 ([2, 5]), 缓存共 5 台`
- 网页「+ 添加电机」也按这个判断，没应答会提示"总线上没有这台"，而不是把缓存当成存在。

✅ 字段解析正确：`_on_rx` 对类型 0 用 `host_id`（bit15~8）作为电机 id，低字节 `0xFE` 忽略
（实测把 GET_ID 发给 1~127 后，电机 2/5/127 的应答都能正确归属）。

### 4.2 运控模式控制指令（类型 1）

| 位置 | 内容 |
|---|---|
| ID bit23~8 | **力矩** [0~65535] ↔ (-12 ~ 12 Nm) |
| ID bit7~0 | 目标电机 CAN ID |
| Byte0~1 | 目标角度 [0~65535] ↔ (-4π ~ 4π) |
| Byte2~3 | 目标角速度 [0~65535] ↔ (-30 ~ 30 rad/s) |
| Byte4~5 | Kp [0~65535] ↔ (0.0 ~ 500.0) |
| Byte6~7 | Kd [0~65535] ↔ (0.0 ~ 5.0) |

本仓库：`send_motion()` 与手册一致（力矩编进 ID、其余大端进数据区）。✅

### 4.3 电机反馈数据（类型 2）★

| 位置 | 内容 |
|---|---|
| ID bit8~15 | **当前电机 CAN ID** |
| ID bit16 | 欠压故障 |
| ID bit17 | 过流 |
| ID bit18 | 过温 |
| ID bit19 | 磁编码故障 |
| ID bit20 | HALL 编码故障 |
| ID bit21 | 未标定 |
| ID bit22~23 | 模式状态：0 Reset / 1 Cali / 2 Motor |
| ID bit7~0 | 主 CAN ID |
| Byte0~1 | 当前角度 [0~65535] ↔ (-4π ~ 4π) |
| Byte2~3 | 当前角速度 [0~65535] ↔ (-30 ~ 30 rad/s) |
| Byte4~5 | 当前力矩 [0~65535] ↔ (-12 ~ 12 Nm) |
| Byte6~7 | 当前温度 = **摄氏度 × 10**（大端） |

- 数据区为**大端** 16 位（实测：温度字节 `01 46` = 326 → 32.6 °C；若按小端会得到 1792.1 °C）。
- 本仓库：`parse_feedback()` 已按上表解析，温度除以 10 输出 °C，并解析 ID 里的故障位/状态位。✅
- ⚠ 角度满量程手册正文写 ±4π，而手册 4.2.1 样例代码与参考库写 ±12.5（差 0.53%）——**待实测确认**（见 §8）。

### 4.4 使能 / 停止 / 设零位 / 改 CAN ID（类型 3 / 4 / 6 / 7）

| 类型 | 数据区 | 备注 |
|---|---|---|
| 3 使能 | 全 0 | — |
| 4 停止 | 全 0 = 正常停止；**Byte0=1 = 清故障** | 本仓库只用了"正常停止" |
| 6 设零位 | Byte0 = 1 | 掉电丢失 |
| 7 改 CAN ID | — | **新 ID 放在 ID 的 bit16~23**：`(7<<24) \| (new_id<<16) \| (master_id<<8) \| target` |

> ⚠ **本仓库 `set_can_id()` 目前把新 ID 写进 `data[0]`，与手册不符**（手册要求放 ID 的 bit16~23），
> 可能导致改 ID 不生效或把 ID 置 0，使用前请先核对/修正（详见 §8）。

### 4.5 单个参数读取 / 写入（类型 17 / 18）

请求（17）：`Byte0~1 = index`，`Byte2~3 = 00`，`Byte4~7 = 00`
应答（17）：`Byte0~1 = index`，`Byte2~3 = 00`，`Byte4~7 = 参数数据`

- **"1 字节数据在 Byte4"** —— 短类型只占低字节，Byte5~7 是**上一次响应的残留**，
  必须按类型宽度只取前 N 字节（1/2/4 字节）。
  实测：读 `0x7005 run_mode` 应答 `05 70 00 00 01 e5 01 46`，真值是 Byte4 的 `01`（位置模式），
  高 3 字节 `e5 01 46` 是残留；若整 4 字节读会得到 `1174529281`。
- 写入（18）掉电丢失；要掉电保存的同类参数见调试表的 `0x2007 / 0x2011~0x2019`。

### 4.6 故障反馈帧（类型 21）

- `Byte0~3` = fault（非 0 表示有故障）：
  `bit0` 电机过温故障（默认 80°C）、`bit1` 驱动芯片故障、`bit2` 欠压、`bit3` 过压、
  `bit4` B 相电流采样过流、`bit5` C 相电流采样过流、`bit7` 编码器未标定、
  `bit8~15` 过载故障、`bit16` A 相电流采样过流
- `Byte4~7` = warning：`bit0` 电机过温预警（默认 75°C）

本仓库：`parse_fault()` 与手册一致 ✅，但目前只有 CLI 使用，Web 侧未展示。

## 6. 运控模式数值映射

| 物理量 | 位置 | 原始范围 | 物理范围 |
|---|---|---|---|
| 角度 | Byte0~1 | 0 ~ 65535 | **-4π ~ 4π**（手册正文）／ **-12.5 ~ 12.5**（手册样例代码 & 参考库） |
| 角速度 | Byte2~3 | 0 ~ 65535 | -30 ~ 30 rad/s |
| Kp | Byte4~5 | 0 ~ 65535 | 0.0 ~ 500.0 |
| Kd | Byte6~7 | 0 ~ 65535 | 0.0 ~ 5.0 |
| 力矩 | **ID bit23~8** | 0 ~ 65535 | -12 ~ 12 Nm |

换算（本仓库 `CanProtocol._float_to_uint` / `parse_feedback`）：

```
原始值 = round((物理值 - MIN) / (MAX - MIN) * 65535)
物理值 = 原始值 / 65535 * (MAX - MIN) + MIN
```

### 已知问题

1. ~~速度模式 PID 预置写错地址~~ **已修**：`set_mode('spd')` 改为读写
   **`0x701F spd_kp` / `0x7020 spd_ki`**（写入值仍是 2.0 / 0.021；手册里 CAN 侧默认值是 1 / 0.002，
   要改默认值另行确认）。⚠ 这 8 个地址需固件 ≥ 1.2.1.5。
2. ~~电压/电流显示用了调试表地址~~ **已修**：改为 **`0x701C VBUS`**（电压）与 **`0x701A iqf`**（电流）。
3. **1 字节参数读成 4 字节**（已修）：`0x7005 run_mode` 曾读出 `1174529281`，正确是 Byte4 = `1`。
4. **反馈帧电机 id 取错字段**（已修）：电机上报帧的电机 id 在 bit15~8，低字节是主机 id(=0)；
   原按低字节取 → `motor_id=0` → 反馈被当噪音整帧丢弃，网页的 pos/vel/trq/tmp 永不更新。
5. **温度未除 10**（已修）：手册规定上报值 = 摄氏度 × 10。
6. **改 CAN ID 的字段位置存疑**：手册要求新 ID 放 **ID 的 bit16~23**，
   本仓库 `set_can_id()` 放在 `data[0]` —— 使用前需核对或修正。
7. **角度满量程待定**：±4π（手册正文）vs ±12.5（手册 4.2.1 样例代码），差 0.53%。
   判定方法：手动转电机轴，比较反馈帧角度与读 `0x7019 mechPos`（float, rad）。
8. **Web 侧未展示故障**：故障帧（类型 21）只有 CLI 在用；反馈帧 ID 里的故障位/状态位
   已解析进 `/api/motors`（`fault_bits` / `state`），但界面还没显示。
9. 反馈帧数据区是**大端**（实测温度 326 = 32.6 °C 印证；若按小端会得到 1792.1 °C）。
